# الخطة التنفيذية لتطوير لوحات Workbench بجودة VS Code

## 1. الهدف

تطوير اللوحات السفلية في المشروع لتقترب من جودة VS Code في **المعمارية، وضوح التفاعل، الاتساق البصري، سهولة الاستخدام، وإمكانية التوسع**، مع الحفاظ على Flutter وبنية المشروع الحالية بدل نسخ تفاصيل TypeScript أو Monaco حرفيًا.

تغطي الخطة:

- Problems
- Output
- Debug Console
- Terminal
- الغلاف المشترك الذي يستضيف هذه اللوحات

هذه خطة تنفيذ متسلسلة وليست اقتراحًا بإعادة كتابة جميع اللوحات. يجب الحفاظ على الخدمات والميزات الموجودة، وخصوصًا نظام الطرفية ذي المخزن المؤقت ومحلل ANSI وإدارة العمليات والتبويبات، وتحسينه عند وجود فجوة محددة فقط.

## 2. مبدأ التنفيذ

توحيد تجربة Workbench لا يعني توحيد نماذج البيانات:

| السطح | نموذج البيانات | مسؤولية واجهة العرض |
| --- | --- | --- |
| Panel shell | حالة التخطيط، التبويب النشط، الحجم، الظهور | احتضان المحتوى وتقديم أوامر اللوحة المشتركة |
| Problems | تشخيصات منظمة حسب URI والمصدر والشدة والموقع | التجميع والتصفية والتنقل إلى موضع التشخيص |
| Output | قنوات وسجلات نصية متدفقة | اختيار القناة، البحث، القراءة، وإدارة التمرير |
| Debug Console | جلسة تصحيح ومدخلات تقييم وعناصر REPL | إدخال التعبيرات وعرض النتائج والقيم المتداخلة |
| Terminal | عمليات/PTy وجلسات طرفية وحالة شاشة تفاعلية | عرض الطرفية والتبويبات والتحكم بالتركيز والحجم |

يجب أن يبقى لكل سطح مصدر حقيقة وخدمة أو متحكم مناسب له. لا تُستخدم قائمة النصوص نفسها لتمثيل التشخيصات أو REPL أو الطرفية.

## 3. خط الأساس في المشروع

استنادًا إلى البنية الحالية:

- [lib/parts/panel/panel_widget.dart](../lib/parts/panel/panel_widget.dart) يعرض التبويبات الأربعة وأزرار إنشاء الطرفية وتكبير اللوحة وإغلاقها.
- [lib/layout/models/layout_state.dart](../lib/layout/models/layout_state.dart) و[lib/layout/controllers/layout_controller.dart](../lib/layout/controllers/layout_controller.dart) يحتفظان بحالة اللوحة واختيار التبويب وتغيير الحجم.
- [lib/parts/panel/views/problems_view.dart](../lib/parts/panel/views/problems_view.dart) يعرض التشخيصات مجمعة حسب URI، لكنه يحتاج إلى تجربة تصفية وتنقل وتفاصيل أكثر اكتمالًا.
- [lib/parts/panel/views/execution_output_view.dart](../lib/parts/panel/views/execution_output_view.dart) يعرض مخرجات جلسة التنفيذ النشطة مع أزرار Run/Stop/Clear والتمرير إلى الأسفل. هذا سطح مخرجات التنفيذ الحالي، وليس بعد سجل قنوات عامًّا مماثلًا بالكامل لقنوات Output في VS Code.
- [lib/parts/panel/views/terminal/terminal_tabbed_view.dart](../lib/parts/panel/views/terminal/terminal_tabbed_view.dart) و[lib/core/terminal/services/terminal_service.dart](../lib/core/terminal/services/terminal_service.dart) يقدمان أساسًا قائمًا للطرفيات والتبويبات والجلسات. توجد خطة مستقلة لتفاصيل نظام الطرفية في [docs/terminal_implementation_plan.md](./terminal_implementation_plan.md)، لذلك تركز هذه الخطة على تكاملها وجودة سطح Workbench، لا على تكرار بناء الطرفية.
- تبويب Debug Console معرف في التخطيط، لكن محتواه الحالي placeholder في [lib/parts/panel/panel_widget.dart](../lib/parts/panel/panel_widget.dart). لا يظهر في خط الأساس المفحوص تكامل محرك تصحيح أو بروتوكول Debug Adapter؛ لذلك لا يجوز تقديم واجهة تقييم توحي بوجود تنفيذ حقيقي قبل تأسيس ذلك.

## 4. معمارية الهدف

```text
WorkbenchLayoutState / Controller
        ↓
PanelShell
  ├── PanelHeader (tabs, badges, shared actions)
  ├── Resize / maximize / visibility behavior
  └── Active Panel View
       ├── ProblemsPanel → DiagnosticsService + ProblemsViewModel
       ├── OutputPanel → OutputService + channel/buffer model
       ├── DebugConsolePanel → DebugSessionService + ReplModel
       └── TerminalPanel → existing TerminalService + terminal instances
```

### قواعد الملكية ودورة الحياة

1. حالة التخطيط تخص `WorkbenchLayoutController`، بينما حالة المرشح أو اختيار العنصر تخص اللوحة المعنية.
2. الخدمات لا تُنشأ داخل `build`; تُنشأ وتُمرّر وفق أسلوب إدارة الاعتمادات المعتمد في التطبيق.
3. تبديل التبويب لا ينبغي أن يمحو حالة اللوحة أو سجلها دون إجراء صريح من المستخدم.
4. إزالة Widget أو إخفاء اللوحة لا يعني قتل عملية طرفية أو جلسة تصحيح تلقائيًا. يجب أن يكون الإنهاء قرارًا صريحًا لخدمة الجلسة.
5. تتعامل كل واجهة مع حالات التحميل والفراغ والخطأ والبيانات؛ لا تستبدل الأخطاء بصمت بواجهة نجاح.
6. إعادة البناء تكون محصورة قدر الإمكان في السطح الذي تغيرت بياناته، ولا تعيد إنشاء عمليات النظام أو محررات الطرفية.

## 5. مراحل التنفيذ المتسلسلة

### المرحلة 0: تثبيت المتطلبات وخط الأساس

**الهدف:** حصر السلوك الموجود والاتفاق على واجهات كل لوحة قبل تغيير الكود.

**المهام**

- مراجعة دورة حياة `PanelWidget`، التخطيط، خدمات Diagnostics/Execution/Terminal، ومواضع حقنها.
- تسجيل السلوك الحالي الذي يجب عدم كسره: اختيار اللوحة، إظهارها، تغيير ارتفاعها، التكبير والاستعادة، إنشاء طرفية، تشغيل ملف، إيقاف التنفيذ، مسح المخرجات، فتح مشكلة.
- تحديد حدود الإصدار: هذه الخطة لا تفترض دعم Debug Adapter أو split terminal غير موجودين.
- اعتماد مواصفات مشتركة لحالات empty/loading/error، واختصارات لوحة المفاتيح، وأسماء الأوامر، وبيانات الوصول.
- فصل العمل غير المرتبط باللوحات عن التنفيذ؛ تبقى تغييرات المستخدم أو التغييرات غير المحفوظة في الشجرة كما هي.

**معيار الإكمال**

- توثيق خط الأساس والواجهات المطلوبة لكل مرحلة.
- وجود قائمة اختبارات مستهدفة قبل بدء إعادة تنظيم واجهة اللوحة.

**اعتماديات:** لا شيء.

---

### المرحلة 1: تقوية Panel shell وتجربة Workbench المشتركة

**الهدف:** جعل السطح المشترك ثابتًا ومتسقًا مثل Workbench في VS Code، دون تحويله إلى مسؤول عن منطق اللوحات.

**المهام**

1. تنظيم `PanelWidget` إلى أجزاء واضحة: رأس اللوحة، عنصر تبويب، أزرار الإجراءات، ومحتوى التبويب النشط؛ مع إبقاء API بسيطًا وعدم بناء abstraction زائد.
2. إبقاء معلومات التبويب (المعرف، الاسم، الشارة، لون/نوع الشارة، وصف الوصول) في تعريف واضح بدل تكرار شروط العرض عند الحاجة.
3. تحسين الشارات: العدد يعكس حالة Problems، وحالة التشغيل تعكس التنفيذ، مع عدم عرض قيمة صفرية أو حالة قديمة.
4. تحديد مسؤولية زر الإضافة حسب التبويب:
   - Terminal: إنشاء طرفية جديدة.
   - Output: لا يعرض زر إنشاء طرفية أو إجراء غير متعلق بالمخرجات.
   - Problems وDebug Console: تعرض إجراءاتها الخاصة عند وجودها، وإلا لا يظهر إجراء مضلل.
5. ضبط شريط التبويبات عند ضيق العرض: تمرير أفقي أو قائمة overflow، من دون قصّ أزرار الإغلاق والتكبير.
6. تحسين التفاعل: مؤشر تبويب نشط واضح، hover/focus states، tooltips، مناطق نقر مناسبة، وتسميات Semantics/keyboard focus.
7. ربط عناصر التحكم بحالة اللوحة المناسبة، مع حماية حدود الحجم ومنع أن تتجاوز اللوحة المساحة المتاحة للتطبيق.
8. ضمان أن `selectPanelTab` يظهر اللوحة وأن الإخفاء/الإظهار لا يغيّر بيانات الجلسات.

**الاختبارات**

- Widget tests للتبديل بين كل التبويبات وأوامر الإظهار/الإخفاء والتكبير.
- اختبار ألا يظهر زر إنشاء Terminal كإجراء عام مضلل عند تبويب غير Terminal.
- اختبار مقاسات شاشة ضيقة وحالات غياب badges.

**معيار الإكمال**

- shell لا يحتوي منطقًا خاصًا بتجميع التشخيصات أو تخزين المخرجات أو دورة حياة REPL.
- كل أوامر الرأس تعمل على اللوحة المقصودة فقط.

**اعتماديات:** المرحلة 0.

### المرحلة 2: إكمال Problems كواجهة تشخيصات قابلة للتنقل

**الهدف:** نقل Problems من قائمة تجميع أساسية إلى واجهة تشخيصات دقيقة، قابلة للترشيح والتنقل، تستند إلى `DiagnosticsService`.

**المهام**

1. تثبيت نموذج التشخيصات وربط عناصر الواجهة بالحقول المتاحة فعليًا: URI، severity، range، message، source، code، related information إن كان دعمها موجودًا في البروتوكول.
2. مراجعة تطبيع مسارات URI واتساقه بين LSP و`DiagnosticsService` وملفات المحرر، بما في ذلك مسح تشخيصات URI عند وصول قائمة فارغة.
3. تصميم نموذج عرض مشتق (ViewModel أو دوال عرض قابلة للاختبار) للتجميع والترتيب والمرشحات، دون نقل ملكية التشخيصات من الخدمة المركزية.
4. إضافة مرشحات واضحة:
   - بحث نصي في الرسالة واسم الملف والمصدر.
   - تشغيل/إيقاف عرض Errors وWarnings وInformation/Hint.
   - قصر النتائج على الملف النشط إذا كان سياق المحرر متاحًا.
   - زر لمسح المرشحات وإظهار عدد النتائج.
5. تنظيم العرض حسب الملف، مع شارة مجموع وإمكانية طي/توسيع المجموعات. الحفاظ على عناصر القائمة خفيفة وكثيفة مثل لوحات IDE.
6. عرض شدة التشخيص وموقعه بطريقة ثابتة، مع التفاف رسالة طويل دون تداخل مع الموقع أو المصدر.
7. تصحيح التنقل: النقر يفتح المورد الموجود أو يركز تبويبه، ثم يحدد/ينقل المؤشر إلى سطر وعمود التشخيص. لا يفتح ملفًا فارغ المحتوى ولا يستبدل محتوى الملف الموجود.
8. إضافة اختيار عنصر متماسك، فتح عند Enter/النقر المزدوج بحسب نمط التطبيق، وإتاحة التنقل بين النتائج إن كانت أوامر المحرر تدعم ذلك.
9. إظهار حالة فارغة دقيقة: لا توجد مشكلات، أو لا توجد نتائج بعد تطبيق المرشحات؛ مع مسح المرشحات من الحالة الثانية.
10. ربط شارة تبويب Problems بالأعداد حسب الشدة، مع تحديثها فور تحديث الخدمة.

**ما يؤجل**

- دعم Quick Fix كامل حتى توجد واجهة Code Actions متكاملة يمكن فتحها من المشكلة.
- جدول أعمدة قابل لإعادة الترتيب إن لم يكن هناك طلب منتج واضح؛ يبدأ التنفيذ بعرض شجري مصقول.

**الاختبارات**

- Unit tests للتصفية والترتيب والتجميع وURI.
- Widget tests للحالات الفارغة، المرشحات، الشارات، الرسائل الطويلة والتفاعل.
- اختبار تكاملي يثبت الانتقال إلى الملف/الموضع الصحيح، بما يشمل ملفًا مفتوحًا مسبقًا وتشخيصًا بعدة أسطر.
- تشغيل اختبارات LSP/Diagnostics المرتبطة؛ لا تستبدل اختبارات المشروع القائمة.

**معيار الإكمال**

- تتطابق القائمة والعدادات والتنقل مع مصدر التشخيصات، ولا تبقى نتائج قديمة بعد حدث مسح.

**اعتماديات:** المرحلة 1. ويمكن تنفيذ إصلاحات نموذج Diagnostics المستقلة بالتوازي فقط إذا لم تغيّر واجهة shell.

### المرحلة 3: تطوير Output إلى سجل قنوات مع الحفاظ على Execution Output

**الهدف:** الحفاظ على واجهة مخرجات التنفيذ الحالية وإضافة حدود معمارية تسمح بقنوات متعددة وبحث وتدفق موثوق، بدل الخلط بين Output والطرفية.

**المهام**

1. تعريف شكل قناة مخرجات وسجلها: معرف ثابت، عنوان، مصدر، نوع الرسالة/المستوى عند توفره، وسجل السطور.
2. إضافة خدمة/مخزن Output مستقل عن Widget وعن `ExecutionController`. يظل ExecutionController مصدر مخرجات التنفيذ، وتُعرض جلساته في قناة مناسبة بدل إنشاء مسار موازٍ يكرر البيانات.
3. دعم قناة مخرجات التنفيذ أولًا، ثم قنوات النظام أو LSP لاحقًا حسب مصادر التطبيق الفعلية. لا تُنشأ أسماء قنوات وهمية.
4. إضافة اختيار القناة، البحث أو التصفية داخل القناة، ومسح السجل للقناة النشطة.
5. تحديد سياسة واضحة لحجم المخزن والسجل، حتى لا ينمو استهلاك الذاكرة بلا حد؛ يكون الحد قابلًا للتبرير والاختبار، لا إعدادًا زائدًا بلا حاجة.
6. تحسين تمثيل stdout وstderr ورسائل النظام مع تباين لوني مناسب، مع بقاء النص قابلًا للتحديد والنسخ.
7. ضمان أن auto-scroll يتبع أحدث البيانات عندما يكون المستخدم عند نهاية السجل، لكنه لا يسحب موضع القراءة قسرًا إذا رجع المستخدم إلى سطور أقدم؛ أظهر إجراء الرجوع إلى الأسفل عند الحاجة.
8. الحفاظ على أزرار Run/Stop المرتبطة بالتنفيذ، وجعل حالة التشغيل والنتيجة النهائية ظاهرتين دون خلطها بحالة الطرفية.
9. توضيح الفرق بصريًا ووظيفيًا بين Output غير التفاعلي وTerminal التفاعلي.

**الاختبارات**

- Unit tests لتخزين القنوات، ترتيب الأحداث، clear، وسياسة الحد الأقصى للسجل.
- Widget tests لاختيار القناة والبحث والتمييز بين stdout/stderr والحفاظ على موضع القراءة.
- اختبارات ExecutionController القائمة أو الجديدة لبدء/إيقاف العملية ووصول الخطوط وحالة الخروج.

**معيار الإكمال**

- يمكن عرض مخرجات التنفيذ في قناة مستقلة من دون نقل منطق تنفيذ الأوامر إلى واجهة Output أو تكرار ملكية الجلسة.

**اعتماديات:** المرحلة 1.

### المرحلة 4: تحديد وتنفيذ نطاق Debug Console الحقيقي

**الهدف:** استبدال placeholder بتصميم صادق وقابل للتوسع، دون عرض REPL ظاهري لا يستطيع تقييم التعبيرات.

**بوابة قرار تقنية**

قبل بناء إدخال REPL، يجب إثبات وجود أو اعتماد تكامل Debug Adapter/محرك تصحيح يوفر:

- جلسة قابلة للبدء والإيقاف وحالة lifecycle.
- تقييم تعبير في سياق الجلسة الحالية.
- أحداث stdout/stderr أو console output.
- تمثيل القيم والمتغيرات القابل للتوسيع إن كان ذلك ضمن النطاق.

إذا لم تتوفر هذه الواجهة، تنفذ المرحلة واجهة حالة غير نشطة واضحة مع توضيح أن جلسة تصحيح غير متاحة، وتُفصل مهمة دعم Debug Adapter في خطة مستقلة. لا يُستخدم تنفيذ shell أو `eval` محلي بديلًا عن تصحيح حقيقي.

**المهام عند توفر الواجهة**

1. تصميم `DebugSessionService` أو Adapter حول الواجهة الفعلية لمحرك التصحيح، مع تجنب ربط Widget ببروتوكول النقل.
2. بناء نموذج REPL لعناصر input/output/error/system event وتحديد الجلسة المالكة لكل عنصر.
3. إنشاء قائمة قابلة للتمرير ومدخل سفلي ثابت، يدعم الإرسال، سجل الأوامر، والنسخ.
4. عرض القيم المعقدة بشكل هرمي قابل للتوسيع، مع تحميل كسول للقيم الفرعية عند دعم المحرك لذلك.
5. إظهار حالة الجلسة (غير متصلة، بدء، متوقفة مؤقتًا، تعمل، منتهية، خطأ) وتفعيل الإدخال فقط في الحالات الصالحة.
6. توفير clear للعرض مع الحفاظ على جلسة التصحيح، وعدم مسح عناصر جلسة أخرى عند تعدد الجلسات.
7. ربط التبويب بأوامر Debug الفعلية فقط؛ لا يعيد استخدام أزرار Run/Stop الخاصة بتنفيذ الملفات إلا إذا كان معناها مطابقًا.
8. تعريف حالات no-session وloading وevaluation-error وsession-ended بتصميم متناسق مع Workbench.

**الاختبارات**

- Unit tests لمحول الجلسة ونموذج REPL وترتيب الأحداث.
- Widget tests للإدخال، سجل الأوامر، مخرجات الأخطاء، القيم القابلة للطي وحالات الجلسة.
- اختبارات مزامنة تمنع نتائج تقييم قديمة من الظهور بعد تبديل الجلسة.

**معيار الإكمال**

- لا تقبل اللوحة تعبيرًا إلا عندما توجد جلسة ومحرك حقيقيان، وتُعرض نتيجة التقييم من المصدر الصحيح.

**اعتماديات:** المرحلة 1، وقرار/تنفيذ دعم Debug Adapter.

### المرحلة 5: مواءمة Terminal مع Panel shell وتحسينات تجربة الاستخدام

**الهدف:** دمج الطرفية القائمة بجودة Workbench من دون إعادة بناء محركها أو فقدان التفاعل والجلسات.

**المهام**

1. مراجعة `TerminalTabbedView` و`TerminalService` ودورة حياة كل `TerminalInstance` مقابل قواعد ملكية الحالة في المرحلة 1.
2. إبقاء شريط تبويبات الطرفيات وأوامر الإغلاق/إنشاء طرفية مرتبطة بتبويب Terminal؛ لا تحذف جلسة عند تبديل لوحة أو إخفائها.
3. ضمان أن إعادة بناء واجهة اللوحة لا تعيد تشغيل shell ولا تفقد المخزن المؤقت أو التركيز الحالي.
4. تحسين حالات البدء والفشل والخروج: رسائل واضحة، إمكانية إنشاء جلسة أخرى، وحالة خروج لا تترك واجهة تبدو نشطة كذبًا.
5. توحيد الألوان، الارتفاعات، toolbar، الأيقونات، hover/focus، وتسميات الوصول مع بقية Workbench، مع إبقاء محرك الطرفية ذا خطوطه وألوانه الخاصة.
6. مراجعة زر Terminal العام في رأس اللوحة: يخلق terminal جديدًا فقط عندما يكون ذلك متوقعًا، ويحوّل المستخدم إلى Terminal بعد الإنشاء.
7. التحقق من سياسة terminal عند إغلاق التطبيق/اللوحة: إيقاف العملية أو إبقاؤها يتبع سلوك المنتج الصريح، لا أثرًا جانبيًا لإزالة Widget.
8. تسجيل الفجوات المنصاتية المعروفة (PTY، resize signaling، shell integration، split panes) وربطها بخطة الطرفية المنفصلة بدل تقديمها كميزات منجزة.

**الاختبارات**

- اختبارات الخدمة لإنشاء جلسات متعددة وتحديد النشطة والإغلاق وترتيب الفهارس.
- اختبارات Widget للتبديل بين tabs مع بقاء الحالة، وحالات فشل الإنشاء.
- تشغيل مجموعة اختبارات الطرفية المركزة وفق [docs/terminal_implementation_plan.md](./terminal_implementation_plan.md).

**معيار الإكمال**

- جلسات الطرفية الموجودة تبقى سليمة عند تغيير تبويب Workbench، ولا تنفذ واجهة الرأس أو إعادة البناء إنشاءً مكررًا غير مقصود.

**اعتماديات:** المرحلة 1، مع إعادة استخدام تنفيذ terminal الموجود.

---

### المرحلة 6: توصيل الأوامر والسياق بين اللوحات والمحرر

**الهدف:** إكمال التفاعل المتبادل الذي يجعل اللوحات جزءًا من IDE لا أجزاء مرئية منفصلة.

**المهام**

- ربط أوامر فتح Problems أو Output أو Debug Console أو Terminal بإظهار اللوحة وتحديد التبويب المناسب.
- ربط Problems بالسياق النشط للمحرر وبالمورد/النطاق، دون فتح محتوى فارغ أو تبويب مكرر.
- إظهار سياق ملف التشغيل في Output، مع الاحتفاظ بهوية الجلسة والقناة.
- ربط focus وإدخال لوحة المفاتيح: عند فتح Terminal ينتقل التركيز إلى الطرفية عند اللزوم؛ وعند فتح Problems يبقى التنقل إلى المحرر مقصودًا.
- التأكد أن اختصارات لوحة المفاتيح وأوامر السياق لا تتعارض بين التبويبات.
- حفظ التبويب النشط والارتفاع إذا كانت آلية persistence موجودة في إعدادات التخطيط؛ لا تضف تخزينًا جديدًا قبل التحقق من نمط المشروع.

**الاختبارات**

- اختبارات controller للتنقل بين panel/editor.
- اختبارات تكامل لأوامر التبديل، التركيز، وسلوك لوحة مخفية.

**معيار الإكمال**

- التبديل إلى أي لوحة من أمر أو سياق يحقق نفس حالة الظهور والتبويب والتركيز المتوقعة كما عند النقر المباشر.

**اعتماديات:** المراحل 2 و3 و5؛ والمرحلة 4 فقط لمسارات Debug Console.

---

### المرحلة 7: التحقق النهائي والتلميع

**الهدف:** تثبيت الجودة المرئية والسلوكية، ومعالجة حالات الحواف قبل اعتبار العمل مكتملًا.

**المهام**

1. مراجعة كل اللوحات تحت الثيمات المدعومة والأحجام الضيقة، بما فيها رسائل طويلة، ملفات كثيرة، مخارج متدفقة، ومحتوى طرفية كثيف.
2. اختبار الأداء: تحديث التشخيصات، وصول output سريع، وتحديث terminal لا يعيد بناء بقية panel بلا ضرورة.
3. اختبار الوصول: قارئ الشاشة، contrast، focus visibility، وتسميات الأزرار/العناصر.
4. مراجعة حالات empty/loading/error/disconnected/session-ended لكل لوحة، والتأكد من وجود فعل مفيد للمستخدم عند الإمكان.
5. فحص الذاكرة ودورة الحياة: إلغاء الاشتراكات والـ controllers والـ scroll controllers، وعدم إبقاء listeners أو عمليات منتهية.
6. تشغيل اختبارات Flutter/Dart الأضيق ذات الصلة أولًا، ثم الاختبارات الأوسع التي يحددها وضع المشروع.
7. إجراء مقارنة مرئية مرجعية مع تصميم VS Code للمبادئ (الكثافة، ترتيب الأدوات، دلالات الشدة، وسلوك التركيز)، لا نسخ بكسلي عشوائي.

**معيار الإكمال النهائي**

- جميع اختبارات المراحل السابقة ناجحة.
- لا يوجد إجراء واجهة يوحي بميزة غير متوفرة.
- لا تُفقد بيانات أو جلسات نتيجة تبديل التبويب أو إخفاء اللوحة.
- لكل لوحة نموذج بيانات ومسؤولية عرض واضحة، والـ Panel shell ينسقها دون امتلاك تفاصيلها.

**اعتماديات:** جميع المراحل السابقة.

## 6. مصفوفة الاختبارات المقترحة

| الطبقة | ما يجب تغطيته |
| --- | --- |
| Unit — Diagnostics | تطبيع URI، تحديث مصدر، مسح النتائج، grouping/filter/sort، وتعداد الشدة |
| Unit — Output | قنوات، ترتيب، clear، التعامل مع تدفق متتابع، وحد السجل |
| Unit — Debug | lifecycle، REPL events، النتائج القديمة، القيم الفرعية، والأخطاء |
| Unit — Terminal | إنشاء/إغلاق/اختيار الجلسات، فشل بدء PTY، وتحرير الموارد |
| Widget — Panel shell | تحديد التبويب، الحالات المرئية، badges، toolbar، الحجم الضيق، focus |
| Widget — Problems | تجميع، مرشحات، empty states، النص الطويل، والتنقل إلى الموضع |
| Widget — Output | اختيار القناة، scroll-follow، حفظ موضع القراءة، stdout/stderr |
| Widget — Debug Console | إدخال/إرسال، عدم وجود جلسة، النتائج والأخطاء والقيم القابلة للطي |
| Integration | تدفق LSP إلى Problems، التنفيذ إلى Output، المحرك إلى Debug Console، PTY إلى Terminal |

## 7. معايير جودة التصميم المستهدفة

لتحقيق جودة قريبة من VS Code، ينبغي مراجعة كل لوحة وفق هذه المعايير:

- **تسلسل بصري واضح:** عنوان/تبويبات، أدوات مرتبطة بالسياق، محتوى، وحالات فارغة مفيدة.
- **كثافة مناسبة للمطور:** معلومات كافية في المساحة المحدودة دون ازدحام أو زخرفة زائدة.
- **إشارات دقيقة:** اللون لا يكون الإشارة الوحيدة للشدة أو الخطأ؛ النص والأيقونة والحالة متوافقة.
- **استجابة متوقعة:** لا تقفز القراءة عند scroll، ولا تفقد الجلسة عند تبديل التبويب، ولا يغيّر زر سياقي لوحة أخرى.
- **اتساق السمة:** استخدام `EditorThemeData` للواجهة العامة وعدم نثر ألوان ثابتة خارج دلالات الطرفية/الشدة.
- **قابلية الوصول:** تلميحات، تسميات، تباين، focus، وتشغيل أساسي بلوحة المفاتيح.
- **الحالات الكاملة:** empty، filtered-empty، loading، disconnected، failed، completed، وactive حسب طبيعة السطح.
- **أداء مستقر:** تحديث البيانات لا يعيد بناء عناصر لا تتأثر، ولا ينسخ سجلات كبيرة بلا داعٍ.
- **شفافية القدرات:** لا تظهر أوامر أو مدخلات تفاعلية لا يوجد خلفها تنفيذ فعلي.

## 8. ترتيب الأولويات والنتيجة المتوقعة

الترتيب الافتراضي:

1. تثبيت خط الأساس.
2. تقوية shell.
3. إكمال Problems؛ فهو الأكثر ارتباطًا بخدمات حالية ويحقق قيمة مباشرة للمحرر.
4. تطوير Output مع إبقاء ExecutionController مالكًا للتنفيذ.
5. تأسيس Debug Console بعد إثبات توفر محرك تصحيح حقيقي.
6. صقل تكامل Terminal وإعادة استخدام المحرك الحالي.
7. وصل الأوامر والسياق ثم التحقق والتلميع.

النتيجة المطلوبة ليست أن تبدو اللوحات الأربع متطابقة، بل أن تتبع لغة Workbench واحدة مع احترام نموذج كل لوحة: Problems للتشخيص، Output للسجل، Debug Console للتقييم ضمن جلسة تصحيح، وTerminal لتفاعل PTY مباشر. هذا هو جوهر نقل جودة VS Code إلى المشروع دون نسخ معماريته حرفيًا.

## 9. مخرجات التنفيذ الحالية

- يحتفظ Panel shell بحالة كل لوحة بعد أول فتح لها عند التبديل، ويعرض شارات التشخيصات وحالة التنفيذ فقط عند وجود قيمة فعلية.
- تدعم Problems البحث في الرسالة والمسار والمصدر والرمز، ومرشحات الشدة والملف النشط، وترتيب النتائج، والتنقل إلى موضعها. فتح ملف مفتوح مسبقًا لا يستبدل محتواه أو تعديلاته غير المحفوظة.
- يوفّر Output قنوات مشتقة من جلسات التنفيذ عبر `OutputService` من دون نسخ سجل السطور أو نقل ملكية العملية من `ExecutionController`. يحتفظ بما يصل إلى 50 جلسة، وبحد أقصى 5000 سطر لكل جلسة، مع البحث والمسح للقناة المختارة والتمرير المتابع للنهاية.
- لا يتوفر Debug Adapter في التطبيق؛ لذلك تعرض Debug Console حالة عدم اتصال واضحة ولا تعرض مدخل تقييم غير فعّال.
- إنشاء الطرفية واختيار اللوحة مرتبطان بتبويب Terminal، وتبقى الجلسات مملوكة لـ `TerminalService` عند تبديل محتوى اللوحة.

تبقى إضافة مصادر Output أخرى، مثل سجل LSP، وتكامل Debug Adapter الحقيقي خارج التنفيذ الحالي إلى أن تتوفر مصادرها وخدماتها الفعلية.
