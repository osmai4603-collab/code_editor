# الخطة التنفيذية لمساطر الأخطاء والتحذيرات في المحرر

## 1. الهدف

إضافة عرض شبيه بـ **Overview Ruler** في الجانب الأيمن من محرر المشروع، بحيث تظهر علامة صغيرة عند موضع كل تشخيص في الملف المفتوح، بلون يتبع شدته. يجب أن تبقى العلامة بمحاذاة السطر الصحيح عند التمرير، وأن تتحدث عند ورود تشخيصات جديدة أو تعديل النص أو تبديل التبويب أو مسح التشخيصات.

تُبنى الميزة على معمارية المشروع الحالية: مصدر التشخيص هو خادم LSP، والحالة المركزية هي `DiagnosticsService`، أما المسطرة فهي طبقة عرض إضافية داخل محرر Flutter. لا تُنقل معمارية Extension Host أو Marker Service الخاصة بـ VS Code حرفيًا؛ المقابل الموجود في التطبيق هو عميل LSP وسجل الخوادم والخدمة المركزية.

## 2. الحالة الحالية والفجوة

المشروع يحتوي بالفعل على معظم أساس تدفق التشخيص:

- [`LspClient`](../lib/core/lsp/client/lsp_client.dart) يستقبل `textDocument/publishDiagnostics` ويفك التشخيصات.
- [`LspServerRegistry`](../lib/core/lsp/registry/lsp_server_registry.dart) يربط خوادم اللغة بـ [`DiagnosticsService`](../lib/core/lsp/diagnostics/diagnostics_service.dart).
- [`ProblemsView`](../lib/parts/panel/views/problems_view.dart) يعرض المشكلات في اللوحة، وميزات الحالة تقرأ أعدادها.
- [`CodeEditorController`](../lib/parts/editor/controllers/code_editor_controller.dart) يقرأ تشخيصات الملف لتنسيق نص السطر.
- [`EditorAreaWidget`](../lib/parts/editor/editor_area_widget.dart) يعرض أرقام الأسطر وشريطي تمرير مخصصين ويتابع تمرير النص.

الفجوة الأساسية هي عدم وجود طبقة Overview Ruler تربط مواقع التشخيص بالارتفاعات على جانب شريط التمرير. وتوجد مسائل في تدفق البيانات ينبغي إصلاحها قبل الرسم:

1. حدث LSP قد يحتوي قائمة تشخيصات فارغة عمدًا لمسح النتائج السابقة، لكن حدث `onDiagnostics` الحالي يحمل القائمة فقط، وسجل الخوادم يتجاهل القوائم الفارغة؛ بالتالي قد تبقى نتائج قديمة.
2. عند وجود عناصر، يستنتج السجل URI من أول عنصر بدل حمل URI مع الحدث؛ لا يمكن لذلك تمثيل حدث المسح الفارغ.
3. الخدمة تخزن قائمة واحدة لكل URI. إذا نشر أكثر من خادم تشخيصاته للملف نفسه، فقد يستبدل تحديث أحدها تحديث الآخر أو يمسحه.
4. ينبغي التحقق من تطابق صيغة المفتاح: الخادم يرسل URI من نوع `file://...`، بينما واجهة المحرر تطلب التشخيصات باستخدام `tabItem.path`. يجب اعتماد تطبيع واحد للقراءة والكتابة.
5. تلوين النص الحالي يرسم التشخيصات المتقاطعة بنمط أحمر واحد، بينما المطلوب التفريق بين Error وWarning وInformation وHint. كما ينبغي ضمان تطبيق النطاقات متعددة الأسطر على كل سطر معنيّ.

## 3. المعمارية المستهدفة

```text
خادم اللغة
  │ textDocument/publishDiagnostics { uri, diagnostics, version? }
  ▼
LspClient
  │ حدث يحمل URI حتى عندما تكون diagnostics فارغة
  ▼
LspServerRegistry
  │ تحديث مملوك لهوية الخادم + URI معياري
  ▼
DiagnosticsService
  ├── ProblemsView / شريط الحالة
  ├── CodeEditorController: تزيين نص النطاق بحسب الشدة
  └── DiagnosticsOverviewRuler: علامات على ارتفاع الأسطر
                                      ▲
                         ScrollController / قياسات المحتوى
```

### مبادئ التصميم

- تظل `DiagnosticsService` المصدر الوحيد للحقيقة، ولا يحتفظ رسام المسطرة بنسخة مستقلة طويلة العمر من التشخيصات.
- يظل `LspClient` مسؤولًا عن فك بروتوكول LSP، و`LspServerRegistry` مسؤولًا عن ربط المصدر بالخدمة، ولا توضع معالجة JSON أو قواعد LSP داخل Widget.
- تكون المسطرة Widget عرضية صغيرة ترسم علامات الملف النشط فقط، وتستقبل التشخيصات وقياسات التمرير من المحرر.
- لا تتداخل المسطرة مع التمرير أو لوحة المفاتيح؛ تكون طبقة الرسم شفافة للتفاعل افتراضيًا، ويظل شريط التمرير الحالي مستقلًا.
- تستخدم مواضع LSP ذات الأساس الصفري داخليًا، وتُحوّل إلى إحداثيات مرئية عند الرسم فقط.
- تكون الألوان جزءًا من `EditorThemeData` لتتبع السمات، لا ألوانًا مبعثرة أو ثوابت داخل الرسام.

### مواءمة مفاهيم VS Code مع المشروع

| مفهوم التحليل المعماري في VS Code | المقابل في المشروع | ما يجب تنفيذه |
| --- | --- | --- |
| مزود اللغة و`publishDiagnostics` | خادم اللغة وإشعار `textDocument/publishDiagnostics` في `LspClient` | الاحتفاظ بـ URI والتشخيصات في كل حدث، بما في ذلك حدث المسح |
| `MainThreadDiagnostics` | ربط `LspServerRegistry` بين عملاء LSP والخدمة | تمرير هوية المصدر والملف إلى الخدمة من دون إسقاط تشخيصات مصادر أخرى |
| `MarkerService` | `DiagnosticsService` | تخزين الحالة المركزية، التجميع، التطبيع، والإشعار بالتغييرات |
| `MarkerDecorationsService` | `CodeEditorController` وتنسيق `TextSpan` | تحويل النطاق والشدة إلى نمط داخل النص |
| `ViewModelImpl` ومجموعات زخارف Overview Ruler | لا يوجد مقابل حالي؛ المكوّن الجديد يجهز علامات الملف النشط | تحويل نطاق LSP إلى علامات وأولويات قابلة للرسم |
| `DecorationsOverviewRuler` | `DiagnosticsOverviewRuler` المقترح | رسم العلامات على طول المحتوى ومحاذاتها للمسطرة اليمنى |
| `OverviewRuler` بجانب شريط التمرير | `EditorScrollbar` الحالي | مشاركة المساحة دون استبدال سلوك الشريط أو اعتراض التفاعل |

الفارق المقصود أن VS Code يملك نموذج نص وتخطيط عرض متكاملًا، بينما يستخدم المشروع `TextField` و`ScrollController` وعمود أرقام أسطر مخصصًا. لذلك يجب اختبار التحويل الهندسي في تطبيق Flutter نفسه، لا افتراض أن إحداثيات VS Code أو ارتفاعات أسطره تنطبق مباشرة.

## 4. خطة المراحل المتسلسلة

### المرحلة 0: تثبيت السلوك المطلوب وخط الأساس

**الهدف:** تعريف الشكل المرئي وحالات دورة الحياة قبل تعديل الكود.

**المهام**

- اعتماد مسار ضيق لعلامات التشخيص بمحاذاة يمين المحرر وقبل/بجوار مسار شريط التمرير، مع إبقاء شريط التمرير ظاهرًا وقابلًا للسحب.
- قصر المسطرة في الإصدار الأول على علامات التشخيص؛ لا تُضاف علامات المؤشر أو البحث أو Git لأنها مصادر مختلفة.
- تحديد الألوان لكل شدة، وقابلية إظهار التشخيصات متعددة الأسطر، والحد الأدنى لحجم العلامة كي لا تختفي الأسطر المتقاربة.
- تحديد أن عرض المسطرة يتبع الملف المفتوح حاليًا فقط، بينما تبقى Problems وشريط الحالة على مستوى مساحة العمل كما هما.
- تسجيل حالات الأساس للاختبار: ملف بلا تشخيصات، تشخيص في أول/آخر سطر، ملف طويل، تبديل تبويب، مسح تشخيصات.

**مخرج المرحلة:** مواصفات قبول واضحة ومتفق عليها، من دون تغيير السلوك الحالي.

**بوابة الانتقال:** لا يبدأ تعديل الرسم قبل الاتفاق على موضع المسطرة وألوان الشدة وسلوك النطاق متعدد الأسطر.

### المرحلة 1: تصحيح عقد بيانات التشخيص ومفاتيح الملفات

**الهدف:** ضمان أن كل تحديث، بما فيه المسح، يصل للملف الصحيح ومن المصدر الصحيح.

**المهام**

1. استبدال حدث `List<DiagnosticItem>` المجرد في حدّ النشر بنموذج حدث يحمل على الأقل `uri` و`diagnostics`، ويمكنه حمل `version` عند توفره. يجب أن يحتفظ بالـ URI حتى عندما تكون القائمة فارغة.
2. تعديل محلل `textDocument/publishDiagnostics` في `LspClient` لإنتاج حدث واحد لكل إشعار، وعدم فقد URI الخاص بالقائمة الفارغة.
3. تعديل اشتراك `LspServerRegistry` ليحدّث الخدمة لكل حدث، بما في ذلك حدث المسح؛ إزالة شرط تجاهل `diags.isEmpty`.
4. إضافة تطبيع URI/path مركزي ومستقر، بحيث تُخزّن البيانات وتُقرأ بالمفتاح نفسه، مع التعامل الصحيح مع URI المشفر والمسارات التي تحتوي مسافات أو أحرفًا غير لاتينية. لا تستخدم قصّ `file://` يدويًا كقاعدة عامة.
5. تمثيل ملكية التشخيصات بحسب معرّف خادم اللغة والـ URI، أو تطبيق دمج مكافئ يضمن ألا يمسح خادم قائمة خادم آخر عند تحديث الملف نفسه.
6. تحديد سلوك `clearForUri` عند إغلاق أو إزالة ملف، ومسح بيانات المالكين المناسبين دون مسح نتائج ملفات أخرى.
7. التأكد من أن getters مثل `getForUri` و`diagnosticsByUri` تعيد قوائم مجمعة غير قابلة للتعديل أو نسخًا آمنة كما يقتضي نمط الخدمة.
8. عند وجود `version` في إشعار الخادم، حفظه واستخدامه لمنع تطبيق نتيجة أقدم من نسخة المستند الحالية؛ لا ترفض إشعارًا لمجرد غياب `version`.
9. تحديد مسح التشخيصات عند إعادة تشغيل عميل LSP أو توقفه، وإلغاء الاشتراكات القديمة قبل ربط عميل بديل حتى لا تعود نتائج من عملية انتهت.

**الملفات المتوقعة:** `core/lsp/client/lsp_client.dart`، `core/lsp/registry/lsp_server_registry.dart`، `core/lsp/diagnostics/diagnostics_service.dart`، ونموذج التشخيص في `core/lsp/protocol`.

**اختبارات المرحلة**

- إشعار LSP عادي ثم إشعار بقائمة فارغة للمورد نفسه يمسح التشخيصات السابقة.
- URI واحد من أكثر من مصدر؛ مسح مصدر لا يمسح المصدر الآخر.
- المسار المحلي وURI المشفر له يرجعان التشخيصات نفسها.
- تحديثات موارد مختلفة لا تتداخل.
- وصول تحديثين بإصداري مستند مختلفين بترتيب معكوس لا يعيد حالة التشخيص إلى إصدار أقدم.
- إعادة تشغيل خادم اللغة لا تترك تشخيصات قديمة أو اشتراكًا مزدوجًا.

**بوابة الانتقال:** لا تعتمد واجهة المحرر على رسم المسطرة حتى تنجح اختبارات المسح والملكية وتطبيع URI.

### المرحلة 2: توحيد تصنيف النطاق والشدة

**الهدف:** جعل تمثيل التشخيص قابلًا لإعادة الاستخدام بالتساوي في النص والمساطر واللوحة.

**المهام**

- إضافة دوال/مساعدات صغيرة مشتركة لاستخراج موضع البداية والنهاية، والتحقق من حدود النطاق، وتحديد ما إذا كان التشخيص يتقاطع مع سطر.
- الاتفاق على تحويل `range.start.line` و`range.end.line` من صفر-أساس إلى هندسة واجهة المستخدم دون إضافة/طرح واحد في أكثر من طبقة.
- التعامل مع النطاق الفارغ، والنطاق الذي ينتهي عند بداية السطر التالي، والنطاق متعدد الأسطر، ومواقع خارج مدى النص بعد تعديل محلي.
- تحديد قاعدة عرض Hint وInformation بوضوح؛ لا تُعامل القيم غير المعروفة كخطأ بصمت، بل تتبع القيمة الافتراضية المعتمدة في نموذج البروتوكول مع اختبارها.
- معالجة فهرسة الأحرف بحسب UTF-16 كما يقتضي LSP عند تلوين النطاق، خصوصًا عند وجود محارف خارج BMP.

**الملفات المتوقعة:** نموذج `DiagnosticItem` أو مساعد نطاق ضمن `core/lsp`; ثم استخدامه من المحرر بدل تكرار حسابات مستقلة.

**اختبارات المرحلة**

- تشخيص عمود واحد ونطاق فارغ ونطاق كامل للسطر ونطاق متعدد الأسطر.
- حدود السطر الأول والأخير، ونطاق يتجاوز النص الحالي، ومحارف Unicode متعددة الوحدات.
- مطابقة لون/فئة كل قيمة `DiagnosticSeverity`.

**بوابة الانتقال:** جميع المستهلكين يتفقون على السطر والنطاق والشدة قبل بناء الرسام.

### المرحلة 3: تحسين زخرفة النص وأرقام الأسطر

**الهدف:** جعل المؤشرات داخل النص متسقة مع علامات Overview Ruler.

**المهام**

- تعديل `CodeEditorController.buildTextSpan` ليختار نمطًا بحسب الشدة: Error وWarning وInformation وHint، بدل تلوين كل تشخيص باللون الأحمر.
- تطبيق النطاق على الأجزاء التي تتقاطع معه بدقة؛ ويجب أن يمتد التشخيص متعدد الأسطر إلى الأسطر التي يغطيها.
- معالجة حالة تداخل نطاقين مختلفي الشدة وفق أولوية معلنة وثابتة، من دون إسقاط تشخيص أو تطبيق نمط غير حتمي.
- تحديث أرقام الأسطر/علامات الهامش لاستخدام الشدة أو إظهار رمز متوافق، بدل اعتبار وجود أي تشخيص خطأً أحمر.
- الحفاظ على ألوان التلوين النحوي والدلالي وتحديد أولوية الزخرفة دون تغيير النص أو مواضع المؤشر والاختيار.
- نقل ألوان التشخيص إلى `EditorThemeData` مع قيم مناسبة للثيم الداكن الحالي، وإضافتها إلى أي ثيمات أخرى عند وجودها.
- اعتماد أولوية صريحة عند تداخل أكثر من شدة في الجزء النصي نفسه؛ المقترح Error ثم Warning ثم Information ثم Hint، مع إبقاء كل التشخيصات متاحة في Problems.

**الملفات المتوقعة:** `parts/editor/controllers/code_editor_controller.dart`، `parts/editor/editor_area_widget.dart`، `core/theme/editor_theme.dart`.

**اختبارات المرحلة**

- Widget/controller tests لكل شدة وللنطاق المتداخل ومتعدد الأسطر.
- التأكد من استمرار semantic tokens وsyntax highlighting بعد تراكب التشخيص.
- التأكد من عدم ظهور مؤشر تشخيص في ملف آخر عند تغيير التبويب.

**بوابة الانتقال:** لا تُنفّذ مرحلة الرسم حتى تكون دلالات الشدة والنطاق متماثلة بين النص والمسطرة.

### المرحلة 4: بناء مكوّن Overview Ruler للرسم

**الهدف:** إنشاء طبقة رسم مسؤولة عن تحويل التشخيصات إلى علامات رأسية ضمن مسار الملف الكامل.

**المهام**

1. إنشاء Widget مستقل، مثل `DiagnosticsOverviewRuler` ضمن `parts/editor/widgets/`، يستقبل قائمة تشخيصات الملف النشط، `ScrollController`، عدد الأسطر، وقياسات الخط/المساحة.
2. استخدام `CustomPaint`/`CustomPainter` لرسم المسار والعلامات بأقل بناء ممكن؛ لا يُنشأ Widget منفصل لكل تشخيص.
3. تحويل رقم السطر إلى Y بنسبة ارتفاع المحتوى الكامل إلى ارتفاع المسار، لا إلى موضع السطر المرئي فقط؛ وبذلك تظل العلامات على طول المسطرة عند التمرير.
4. أخذ قياسات المحتوى الحقيقية من تخطيط المحرر الحالي أو من مصدر موحد لارتفاع السطر؛ لا تعتمد قيمة 13.5 أو معامل ارتفاع الخط في أكثر من موضع يدوي. يجب أن يطابق القياس نمط النص والحشو وارتفاع السطر المستخدم فعليًا في `TextField` وهامش أرقام الأسطر.
5. ربط نطاق متعدد الأسطر بامتداد مرئي ملائم، مع دمج علامات الشدة الواحدة المتجاورة لتحسين المقروئية والأداء.
6. تحديد تراكب العلامات المتزامنة في السطر نفسه: إما اختيار أعلى شدة (Error ثم Warning ثم Information ثم Hint) أو عرض lanes متعددة إذا كانت المساحة تسمح؛ يجب اختيار سياسة واحدة واختبارها.
7. دعم حالات المسار الصغير، أو محتوى لا يتجاوز viewport، أو غياب `ScrollPosition`، أو خلو الملف من التشخيصات من دون قسمة على صفر أو أخطاء بناء.
8. جعل الرسام غير تفاعلي في النسخة الأولى (`IgnorePointer`) حتى لا يعترض سحب شريط التمرير أو اختيار النص.

للمسطرة ذات الارتفاع `H` وعدد أسطر `N`، يمكن بدء الحساب بمركز سطر `i` عند `((i + 0.5) / N) * H` بعد حصر `i` إلى `[0, N - 1]`. ويحوّل نطاق التشخيص إلى امتداد بين مركزي سطر البداية والنهاية، مع حد أدنى للارتفاع وحصره داخل حدود الرسم. وبما أن نهاية نطاق LSP غير شاملة، فإذا انتهى النطاق عند العمود صفر من سطر لاحق، فلا ينبغي اعتباره تغطية لذلك السطر. هذه نقطة بداية لا بد من معايرتها مقابل قياسات المحرر الفعلية؛ لا تستخدم إزاحة التمرير مرتين لأن المسطرة تمثل المستند كاملًا، لا نافذة العرض فقط.

**الملفات المتوقعة:** مكوّن رسم جديد، وتعديلات محدودة في `editor_area_widget.dart` و`editor_theme.dart`.

**اختبارات المرحلة**

- اختبارات وحدة لحساب إحداثيات السطور والارتفاعات والنطاقات المتعددة.
- اختبارات Widget لمحتوى قصير وطويل وتشخيصات عند البداية والنهاية.
- تحقق بصري من تطابق مواضع العلامات مع أرقام الأسطر عبر أكثر من حجم نافذة.

**بوابة الانتقال:** اجتياز اختبارات تحويل الإحداثيات قبل الربط مع شريط التمرير.

### المرحلة 5: دمج المسطرة مع تخطيط المحرر ودورة حياته

**الهدف:** عرض المسطرة في المكان الصحيح وربطها بتحديثات المحرر والتشخيصات.

**المهام**

- إدراج المكوّن في الـ `Stack` المستخدم حاليًا في `EditorAreaWidget` بمحاذاة اليمين، مع إبقاء مسار `EditorScrollbar` في موضعه وتفاعله.
- توفير مساحة عرض محسوبة لا تغطي آخر أحرف السطر ولا تقلص مساحة نص المحرر بشكل غير متوقع؛ إذا تطلب التخطيط حجز عرض، فينبغي تعديل عرض محتوى المحرر ومقياس التمرير معًا.
- استخدام تشخيصات URI للتبويب النشط فقط، مع إعادة بناء عند تغير `DiagnosticsService`؛ لا يكفي أن يستمع المحرر إلى `_lspExtension` وحده.
- ربط تحديث علامات المسطرة بتغيّر عدد الأسطر، قياسات المحتوى، تغيّر أبعاد viewport، تغيّر التشخيصات، وتبديل التبويب.
- ضمان عدم وجود Listener مكرر على `ScrollController`، وإلغاء الاشتراكات/المؤقتات في `dispose`.
- المحافظة على مسح التشخيصات عند ورود قائمة فارغة، وعند إغلاق ملف أو تبديل مصدر الخادم حسب سياسة المرحلة 1.

**اختبارات المرحلة**

- تغيير التبويب بين ملفين لكل منهما تشخيصات مختلفة، ثم العودة.
- تحديث تشخيصات الملف أثناء التمرير وعدم الحاجة إلى إعادة فتحه.
- مسح التشخيصات أثناء وجود الملف على الشاشة وإزالة العلامات فورًا.
- سحب الشريط الرأسي فوق/بجوار المسطرة، وتمرير النص أفقيًا، والتحقق من عدم اعتراض الإدخال.
- إعادة بناء/تغيير قياس المحرر بعد تغيير حجم النافذة أو إضافة/حذف أسطر، والتحقق من بقاء العلامات متناسبة مع ارتفاع المحتوى.

**بوابة الانتقال:** نجاح حالات الدورة الحية والتفاعل قبل إضافة سلوك النقر أو التحسينات الاختيارية.

### المرحلة 6: الألوان، الإتاحة، وتحسين تجربة الاستخدام

**الهدف:** إتمام التناسق البصري وإمكانية الوصول.

**المهام**

- إضافة ألوان `error` و`warning` و`information` و`hint` إلى الثيم، وتوثيقها مع ألوان التمرير الحالية.
- مراعاة تباين اللون مع خلفية المحرر في الوضع الداكن؛ لا تعتمد على اللون وحده إذا أضيفت تسمية أو تفاعل.
- وضع حد أدنى للارتفاع وعرض قابل للضبط داخليًا بحسب مساحة المسطرة، وتخفيف كثافة العلامات المتقاربة من دون إخفاء اختلاف الشدة.
- إضافة Semantics للمسطرة بوصفها ملخصًا بصريًا غير تفاعلي، مع إبقاء تفاصيل الرسالة في Problems/hover إن أضيف لاحقًا.
- تقييم الأداء على ملف كبير وعدد تشخيصات مرتفع؛ حساب نقاط الرسم عند تغيّر البيانات أو القياسات بدل كل إعادة بناء غير مرتبطة.
- (اختياري بعد ثبات MVP) دعم النقر على علامة للانتقال إلى السطر، مع حساب `ScrollController` من موضع العلامة وإبقاء سلوك السحب واضحًا.

**اختبارات المرحلة**

- اختبار قيم الثيم وتغير الثيم دون إعادة إنشاء حالة الملف.
- اختبار Semantics الأساسية، وفحص تباين بصري يدوي.
- اختبار أداء تقريبي بعدد كبير من التشخيصات وتغييرات التمرير المتتابعة.

### المرحلة 7: التحقق الشامل والتوثيق

**الهدف:** التحقق من الميزة من مصدر LSP إلى الشاشة، لا من الرسام وحده.

**المهام**

- تحديث اختبارات `lsp_client_test.dart` لعقد إشعارات التشخيصات بما فيها المسح.
- إضافة اختبارات مستقلة لـ `DiagnosticsService` لملكية المصادر وتطبيع URI.
- إضافة اختبارات editor/controller لمطابقة النطاقات والشدة.
- إضافة اختبارات لـ `DiagnosticsOverviewRuler` لحساب النقاط، lifecycle، الملف النشط، والتفاعل مع scroll metrics.
- تشغيل `flutter test` على الملفات المتأثرة أولًا، ثم مجموعة الاختبارات الكاملة عند اجتيازها.
- تشغيل `flutter analyze` على المشروع للتحقق من الأنواع والتحذيرات.
- توثيق كيفية إضافة ألوان التشخيصات، مصادر العلامات، وحدود الميزة في صفحة `docs`.
- إجراء تحقق يدوي مع خادم Dart LSP وملف يحوي أخطاء وتحذيرات في أول الملف ووسطه وآخره، ثم تعديل النص ومسح التشخيصات وتبديل التبويبات.

**معيار الإكمال:** لا توجد علامات قديمة بعد المسح أو تبديل الملف؛ الألوان والمواضع متوافقة مع التشخيصات؛ شريط التمرير والنص يحتفظان بسلوكهما؛ الاختبارات والتحليل ثابتان.

## 5. ترتيب التنفيذ والاعتماديات

```text
المرحلة 0: تثبيت السلوك
        ↓
المرحلة 1: عقد البيانات، الملكية، URI والمسح
        ↓
المرحلة 2: دلالات النطاق والشدة
        ↓
المرحلة 3: زخارف النص وأرقام الأسطر
        ↓
المرحلة 4: مكوّن الرسم وحساب الإحداثيات
        ↓
المرحلة 5: الدمج ودورة الحياة
        ↓
المرحلة 6: الألوان والإتاحة والأداء
        ↓

```

## 6. معايير القبول النهائية

- يظهر لكل تشخيص في الملف النشط مؤشر في موضع السطر/النطاق على يمين المحرر.
- تميّز الألوان بين Error وWarning وInformation وHint وفق الثيم.
- تتبع العلامة المحتوى كاملًا، ولا تتحرك إلى موضع خاطئ عند تمرير viewport.
- تتطابق URI المستخدمة في خدمة التشخيصات مع URI الملف المفتوح، بما في ذلك المسارات المشفرة.
- يؤدي إشعار تشخيصات فارغ إلى إزالة العلامات السابقة دون تأخير غير مبرر.
- لا يؤدي مسح مصدر واحد إلى حذف تشخيصات مصدر آخر للملف نفسه.
- تُحدّث العلامات عند تغيّر التشخيصات أو فتح/إغلاق/تبديل الملفات.
- يبقى Problems View وشريط الحالة والتسطير داخل النص متزامنة مع الخدمة المركزية.
- لا تعترض المسطرة إدخال النص أو السحب أو التمرير، ولا تظهر أخطاء عند غياب أبعاد التمرير.
- تجتاز الاختبارات المستهدفة و`flutter analyze`، ويؤكد الفحص اليدوي صحة العرض على ملف طويل.

## 7. المخاطر والقرارات الواجب حسمها أثناء التنفيذ

| المسألة | الخطر | التوجيه المقترح |
| --- | --- | --- |
| URI مقابل مسار الملف | بيانات صحيحة لكن `getForUri` يعيد قائمة فارغة | تطبيع مركزي وفصل تحويل URI عن Widgets |
| تشخيص فارغ | بقاء علامات قديمة بعد إصلاح الكود | تضمين URI في حدث النشر حتى مع قائمة فارغة |
| أكثر من خادم/مصدر | الاستبدال أو المسح المتبادل | تخزين لكل مالك ثم تجميع عند القراءة |
| إحداثيات السطر | العلامات لا تصطف بسبب اختلاف ارتفاع الخط أو الحشو | مصدر قياس واحد مطابق لتخطيط TextField |
| تمرير/تغيير قياس المحتوى | مواضع غير مستقرة بعد تغيير النص أو حجم النافذة | حساب من ScrollMetrics الفعلية وجدولة تحديث بعد layout عند الضرورة |
| نتائج LSP بترتيب وصول مختلف | نتيجة قديمة تستبدل تشخيصات إصدار أحدث | تحقق من version عندما يرسله الخادم، مع مسح/تحديث متسق عند غياب الإصدار |
| نطاق متعدد الأسطر | ظهور علامة عند البداية فقط أو امتداد مبالغ فيه | سياسة موحدة للنطاق، واختبار الحدود قبل الرسم |
| تراكم علامات كثيرة | ازدحام بصري أو بطء الرسم | تجميع العلامات المتجاورة وحدود رسم قابلة للقياس |
| تفاعل الرسم | المسطرة تمنع سحب الشريط أو تحديد النص | طبقة غير تفاعلية افتراضيًا؛ أضف النقر كخطوة منفصلة |
