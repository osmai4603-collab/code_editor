# الخطة التنفيذية لبناء نظام إعدادات لمحرر الأكواد

## 1. الغرض والمرجع

تحدد هذه الوثيقة خطة عملية لبناء نظام إعدادات مركزي في مشروع Flutter `code_editor`، مستلهماً المبادئ المعمارية التي ظهرت في تحليل إعدادات VS Code: تعريف الإعدادات في سجل واضح، فصل مصادر القيم، حساب القيمة الفعالة وفق الأولوية والنطاق، واجهة موحدة للقراءة والكتابة، ومكونات واجهة تستهلك الخدمة بدلاً من امتلاك التخزين الخاص بها.

الهدف هو نقل المشروع تدريجياً من تفضيلات محلية متفرقة إلى نظام يمكن اختباره وتوسيعه، من دون نسخ Extension Host أو ملفات التعريف أو تعقيد الإعدادات البعيدة في VS Code. المرجع التحليلي الأصلي موجود في `/home/osm/Downloads/vscode-main/vscode-main/docs/vscode-settings-architecture.ar.md`.

هذه خطة تنفيذ وليست تغييراً للشيفرة. كل مرحلة تنتج قيمة مستقلة قابلة للمراجعة، مع توضيح تبعيات المراحل ومعايير قبولها.

## 2. صورة المشروع الحالية

تظهر مراجعة المشروع أن هناك بالفعل نقاط بداية مفيدة، لكن لا توجد خدمة إعدادات عامة أو شاشة إعدادات شاملة بعد:

- [main.dart](../lib/main.dart) ينشئ الخدمات ويوفرها عبر `InheritedNotifier` scopes. هذا هو مكان الربط الطبيعي لخدمة الإعدادات ومخازنها، مع المحافظة على نمط الحقن الموجود بدلاً من إضافة حزمة إدارة حالة جديدة.
- [EditorThemeData](../lib/core/theme/editor_theme.dart) يحتوي لوحة ألوان ثابتة ويصل إلى الواجهة عبر `EditorTheme`، لكن اختيار الثيم ليس إعداداً محفوظاً بعد.
- [WorkbenchLayoutState](../lib/layout/models/layout_state.dart) و[WorkbenchLayoutController](../lib/layout/controllers/layout_controller.dart) يديران ظهور الأجزاء وأبعادها في الذاكرة.
- [TerminalConfigService](../lib/core/terminal/services/terminal_config_service.dart) يحمل إعدادات طرفية افتراضية في `ChangeNotifier`، لكنها غير موصولة بمخزن دائم موحد.
- [StatusBarService](../lib/core/statusbar/status_bar_service.dart) يملك تفضيل إخفاء العناصر ويقرأه عبر [StatusBarPreferencesStore](../lib/core/statusbar/status_bar_preferences_store.dart)، الذي يستخدم `SharedPreferences` ويعرض واجهة مخزن in-memory للاختبارات.
- [FileExplorerController](../lib/core/file_system/controllers/file_explorer_controller.dart) يعرف مجلد Workspace ويحفظ بعض حالة المستكشف؛ المشروع الحالي لا يملك نموذجاً عاماً لملف إعدادات Workspace.
- تحتوي الواجهة على نقاط قابلة لعرض الإعدادات، لكن يلزم بناء صفحة/محرر لها وتحديد طريقة استدعائها.

> **احتياط تكاملي:** مساحة العمل تحتوي تغييرات محلية غير ملتزمة في خدمات وواجهات ووثائق عديدة. عند تطبيق هذه الخطة، يجب مراجعة `git status` والفروق قبل كل مرحلة، وتعديل الملفات بالتكامل مع هذه التغييرات دون استبدالها أو التراجع عنها. الخطة لا تستهدف اختبار شريط التمرير ولا تتطلب تعديل ملفه.

## 3. النتيجة المستهدفة

عند اكتمال المراحل الأساسية، ينبغي أن يستطيع التطبيق:

1. تعريف كل إعداد مرة واحدة مع مفتاح ثابت ونوع وقيمة افتراضية ونطاق ووصف ومُتحقق.
2. قراءة قيمة فعالة عبر خدمة واحدة، سواء استهلكتها واجهة أو controller أو خدمة طرفية.
3. دعم مصادر إعداد محددة وواضحة في النسخة الأولى: الافتراضي، المستخدم المحلي، وWorkspace الحالي.
4. تطبيق أولوية ثابتة: `الافتراضي < المستخدم < Workspace`، بحيث تتغلب قيمة Workspace عند وجودها على قيمة المستخدم.
5. إظهار مصدر القيمة وفصل القيمة الفعالة عن القيم المخزنة لأغراض التشخيص.
6. حفظ التغييرات بعد التحقق منها، وإظهار أخطاء التخزين أو الإدخال بدلاً من إخفائها.
7. تغيير الإعداد في وقت التشغيل وإبلاغ المستهلكين المعنيين فقط.
8. توفير صفحة إعدادات قابلة للبحث والتصفية والتعديل، مع إبقاء التحرير اليدوي لملف Workspace خياراً ممكناً.
9. الحفاظ على السلوك الافتراضي الحالي للمظهر والتخطيط والطرفية وشريط الحالة أثناء الترحيل.

## 4. قرارات النطاق المعماري

### ضمن الإصدار الأول

- أنواع الإعدادات الأساسية اللازمة للمشروع: `bool`, `int`, `double`, `String`، وقيم تعداد عبر تعريف مضبوط.
- مصادر `default`, `user`, `workspace`.
- ملفات إعدادات Workspace بصيغة JSON في `.vscode/settings.json` عندما يثبت دعم الكتابة على منصة التشغيل المستهدفة. يبقى مخزن المستخدم في `SharedPreferences` في النسخة الأولى.
- خدمة مركزية typed مع عمليات `get`, `inspect`, `update`, وإشعار تغيّر.
- دمج الثيم، بعض مفاتيح التخطيط الدائمة، الطرفية، وتفضيلات إظهار عناصر Status Bar.
- تحقق من صحة البيانات عند القراءة والكتابة، وإبلاغ واضح عن الفشل.

### خارج النطاق الأولي

- إعدادات متعددة الجذور، إعدادات مستخدم بعيدة، ملفات تعريف مستخدم متعددة، سياسات مؤسسة، مزامنة سحابية، وتجارب A/B.
- مساهمة إعدادات من امتدادات خارجية، أو واجهة Extension API.
- إعدادات لغة مثل `[dart]` حتى يُحسم وجود استخدام عملي لها.
- نظام Workspace Trust كامل. إلى أن يوجد هذا النظام، لا ينبغي وصف ملفات Workspace بأنها آمنة أو تفعيل إعدادات تنفيذية خطرة تلقائياً.
- استيراد/تصدير شامل للتفضيلات، أو إدارة تعارضات متقدمة بين عدة نوافذ للتطبيق.

هذه الحدود تمنع بناء بنية أكبر من حاجة التطبيق الحالي، مع إبقاء العقود قابلة لإضافة مصدر أو سياق لاحقاً.

## 5. المعمارية المقترحة

```text
تعريف الإعدادات (Registry)
  ├─ المفتاح والنوع والقيمة الافتراضية والوصف والنطاق والتحقق
  └─ مخطط الواجهة والبحث
             |
             v
ConfigurationService
  ├─ get(key, context) -> القيمة الفعالة
  ├─ inspect(key, context) -> قيمة كل مصدر ومصدر القيمة الفعالة
  ├─ update(key, value, target, context)
  └─ أحداث تغيّر مفهرسة بالمفاتيح
       |                         |
       v                         v
User Settings Store        Workspace Settings Store
SharedPreferences           .vscode/settings.json
       \                         /
        \                       /
         ------ ConfigurationModel
                         |
             Settings UI + feature controllers
```

### مبادئ التصميم

1. **تعريف من النوع نفسه:** لا تمرر إعدادات غير متحققة كـ `Map<String, dynamic>` إلى الميزات. الخرائط تظل تفصيلاً داخلياً للتخزين وقراءة JSON.
2. **الخدمة هي واجهة القراءة والكتابة:** لا تستدعِ `SharedPreferences` من Widget أو controller خاص بميزة.
3. **المصدر لا يساوي القيمة:** يجب أن تتيح خدمة الفحص معرفة الافتراضي والمخزن للمستخدم وWorkspace والقيمة النهائية.
4. **تحديثات ذات معنى:** يصدر الحدث فقط عند اختلاف القيمة الفعالة أو معلومات المصدر المؤثرة، مع المفاتيح المتغيرة.
5. **قابلية الحقن:** مخازن المستخدم وWorkspace واجهات يمكن استبدالها بـ in-memory stores في الاختبارات.
6. **لا افتراض بأن كل المفاتيح تدعم كل المصادر:** تحدد metadata النطاق المسموح، وترفض عملية الكتابة غير الصالحة.
7. **عدم إخفاء الأخطاء:** فشل القراءة/الكتابة يظهر في حالة الخدمة أو يعود كخطأ إلى المستدعي، ويعالج عند حد واجهة المستخدم برسالة واضحة.

### نموذج تعريف الإعداد

المفهوم المطلوب في Dart، بصرف النظر عن شكل الكلاسات النهائي:

```text
SettingDefinition<T>
  key: String
  defaultValue: T
  scope: application | user | workspace
  description/category/order: metadata للواجهة
  validate(value): نتيجة تحقق أو خطأ مفهوم
  decode/encode: تحويل نوعي للتخزين
```

يفضل تعريف إعدادات التطبيق في ملفات كتالوج مقسمة حسب المجال، مثل `editor_settings.dart` و`terminal_settings.dart`، بدلاً من كتلة عملاقة. لا يلزم إنشاء نظام تسجيل ديناميكي إذا كانت قائمة التعريفات ثابتة ومجمعة وقت البناء؛ يمكن أن يكون السجل خريطة typed مركزية تُبنى من هذه التعريفات.

## 6. مراحل التنفيذ

### المرحلة 0: توثيق خط الأساس وتحديد مفاتيح الإصدار الأول

**الهدف:** تثبيت السلوك الحالي قبل توحيد مصادر الإعدادات.

**المهام**

1. مراجعة الفروق المحلية في الملفات التي ستتأثر، خصوصاً `main.dart` و`editor_theme.dart` و`layout_controller.dart` و`terminal_config_service.dart` وخدمة Status Bar.
2. حصر القيم التي ينبغي تحويلها لإعدادات، وتصنيفها إلى:
   - تفضيلات دائمة للمستخدم.
   - تفضيلات مرتبطة بWorkspace.
   - حالة جلسة مؤقتة لا ينبغي حفظها كإعداد.
3. تحديد القيم الافتراضية الحالية كما تظهر للمستخدم؛ لا تغيرها لمجرد إدخال النظام الجديد.
4. إنشاء جدول مفاتيح أولي يشمل الحد الأدنى:

| المجال | مفتاح مقترح | افتراضي البداية | المصدر المقترح |
| --- | --- | --- | --- |
| المظهر | `workbench.colorTheme` | `darkModern` | المستخدم |
| التخطيط | `workbench.statusBar.visible` | `true` | المستخدم |
| التخطيط | `workbench.activityBar.visible` | `true` | المستخدم |
| التخطيط | `workbench.sidebar.visible` | `true` | مستخدم أو Workspace بعد تثبيت السياسة |
| التخطيط | `workbench.panel.visible` | `true` | مستخدم أو Workspace بعد تثبيت السياسة |
| المحرر | `editor.scrollbar.visibility` | `auto` | المستخدم ثم Workspace |
| الطرفية | `terminal.fontSize` | `13` | المستخدم ثم Workspace |
| الطرفية | `terminal.scrollback` | `1000` | المستخدم ثم Workspace |
| Status Bar | `statusBar.hiddenEntryIds` | مجموعة فارغة | المستخدم |

1. فصل القيم السلوكية المؤقتة مثل `isZenMode`، التبويب النشط، مؤشر الكتابة، وحالة المؤشر عن الإعدادات الدائمة إلا إذا اتخذ قرار منتج صريح بحفظها.

**المخرجات ومعيار الخروج**

- قائمة مفاتيح وقيم افتراضية ونطاقات متفق عليها ومكتوبة في الخطة أو جدول التنفيذ.
- اختبارات السلوك الحالية المحددة كخط أساس.
- لا تغييرات وظيفية مطلوبة في هذه المرحلة.

**الاعتماد:** لا شيء. يمكن إنجازها بمعزل عن بقية المراحل.

### المرحلة 1: كتالوج الإعدادات والتحقق النوعي

**الهدف:** تأسيس مصدر واحد لتعريف المفاتيح الافتراضية وقواعد صلاحيتها.

**المهام**

1. إنشاء مساحة مناسبة مثل `lib/core/settings/definitions/` و`lib/core/settings/models/`.
2. تعريف `SettingDefinition<T>` typed مع المفتاح والقيمة الافتراضية والنطاق والوصف والفئة وترتيب العرض ومتحقق القيمة.
3. تنفيذ تعريفات immutable لقائمة المرحلة 0، باستخدام أنواع Dart الصريحة أو enums لمجموعات القيم المقيدة.
4. إنشاء `SettingsRegistry` يتحقق عند بدء التشغيل من عدم تكرار المفتاح، وتوافق قيمة الافتراضي مع النوع، وصحة metadata.
5. وضع حدود رقمية معقولة حيث يلزم (مثلاً حجم الخط، ارتفاع السطر، وعدد أسطر scrollback) وتحديد سياسة قصّ/رفض القيمة خارج المجال. القرار الافتراضي الموصى به: رفض غير الصالح مع خطأ مفهوم، لا تحويل صامت.
6. توفير اختبار لكل تعريف أساسي واختبار لتكرار المفاتيح والقيم الافتراضية غير المتوافقة.

**مخرجات مقترحة**

- `lib/core/settings/models/setting_definition.dart`
- `lib/core/settings/settings_registry.dart`
- ملفات كتالوج صغيرة بحسب المجالات.
- `test/settings/settings_registry_test.dart`

**معيار القبول**

- يمكن الحصول على أي إعداد بالـ key مع نوع وقيمة افتراضية ثابتة.
- لا يعتمد أي Widget على نص مفتاح مكتوب يدوياً خارج الكتالوج أو موضع ربط موثق.
- يفشل الاختبار بوضوح عند تعريف مفتاح مكرر أو قيمة افتراضية غير صالحة.

**الاعتماد:** المرحلة 0.

### المرحلة 2: نماذج المصادر وحل القيمة الفعالة

**الهدف:** تطبيق قاعدة الأولوية مركزياً وفصلها عن التخزين والواجهة.

**المهام**

1. تعريف `SettingTarget` ومعلومات السياق الدنيا، مثل `workspacePath` عند القراءة أو الكتابة إلى Workspace.
2. تعريف `SettingsSnapshot` أو نماذج مماثلة لتمثيل قيم المصادر، والقيمة الفعالة، ومصدرها.
3. بناء resolver يقرأ الافتراضي ثم المستخدم ثم Workspace، ويطبق أولوية موثقة واحدة.
4. تطبيق النطاق: إعداد `user` لا يكتب إلى Workspace، وإعداد `workspace` فقط يسمح بتجاوزه في المصدر المسموح؛ لا تُخفى أخطاء الهدف المخالف.
5. تعريف الحدث `SettingsChange` الذي يحمل المفاتيح المتأثرة والمصدر/الهدف، وتجنب إرسال إشعار عام عند تعديل لا يغير القيمة.
6. تنفيذ `inspect(key, context)` كي تستطيع الواجهة المستقبلية عرض «القيمة الفعالة» و«مصدرها».
7. اختبار أولوية المصادر، غياب القيم، القيمة الفارغة مقابل الغائبة، والنطاق غير المسموح.

**معيار القبول**

- تعطي الحالات المتضاربة نتيجة متسقة مع الترتيب `default < user < workspace`.
- يمكن اختبار resolver بالكامل من دون Flutter Widgets أو SharedPreferences أو ملفات حقيقية.
- لا يتم الخلط بين `null` كقيمة مشروعة وبين غياب مفتاح إلا وفق تمثيل صريح في التعريف.

**الاعتماد:** المرحلة 1.

### المرحلة 3: واجهات التخزين ومخزن المستخدم

**الهدف:** حفظ إعدادات المستخدم عبر الواجهة النوعية الجديدة، وتوفير طريق ترحيل آمن لتفضيلات Status Bar الحالية.

**المهام**

1. تعريف عقدي التخزين، مثل `UserSettingsStore` و`WorkspaceSettingsStore`، مع عمليات تحميل/كتابة واضحة وأخطاء متوقعة.
2. بناء مخزن مستخدم فوق `SharedPreferences`، يكتب تمثيلاً JSON/versioned تحت مفتاح تخزين واحد أو مفاتيح مستقرة بإصدار واضح.
3. تحويل القيم بواسطة definitions في registry، والتحقق من القيم المسترجعة قبل قبولها.
4. تحديد التعامل مع بيانات قديمة أو تالفة: عدم تحويل البيانات التالفة إلى نجاح صامت؛ أبلغ حالة تعافٍ مفهومة، واحتفظ بالقيمة الافتراضية للمفتاح المتأثر فقط أو اعرض خطأ بدء الخدمة بحسب سياسة المنتج.
5. ترحيل `status_bar.hidden_entry_ids` إلى المفتاح المركزي الجديد. اجعل الترحيل idempotent (تكراره آمن)، ولا تحذف القيمة القديمة إلا بعد نجاح كتابة الجديدة.
6. تقديم in-memory store للاختبارات، وعدم ربط اختبارات الخدمة بمخزن النظام.
7. تسلسل الكتابات أو دمجها لتجنب ضياع تغييرات متقاربة زمنياً. عند فشل الحفظ، ارجع الخطأ ولا تعرض واجهة النجاح على أنه دائم.

**مخرجات مقترحة**

- `lib/core/settings/storage/user_settings_store.dart`
- `lib/core/settings/storage/shared_preferences_user_settings_store.dart`
- `test/settings/user_settings_store_test.dart`
- اختبارات ترحيل `StatusBarPreferencesStore`.

**معيار القبول**

- تعود تفضيلات المستخدم بعد إعادة إنشاء الخدمة.
- ترفض البيانات التي لا تطابق نوع التعريف مع تشخيص واضح.
- نجاح الترحيل لا يفقد قائمة عناصر الشريط المخفية.
- فشل الكتابة يمكن ملاحظته من المستدعي والاختبار.

**الاعتماد:** المرحلة 2.

### المرحلة 4: خدمة الإعدادات وربط دورة حياة التطبيق

**الهدف:** توفير واجهة واحدة للقراءة والتحديث وإتاحتها لكل أجزاء التطبيق.

**المهام**

1. إنشاء `SettingsService extends ChangeNotifier` أو عقد خدمة مناسب للنمط الحالي، يعتمد على السجل والمخازن ولا يملك تفاصيل الواجهة.
2. توفير واجهات typed مثل `get<T>(definition, context)`, `inspect`, و`update`، مع منع update غير الصالح أو غير المسموح.
3. تهيئة الخدمة قبل بناء الشجرة التي تعتمد إعداداتها، باستخدام نمط التهيئة asynchronous الموجود في `main.dart` أو bootstrapping مخصص.
4. إضافة `SettingsScope` باستخدام `InheritedNotifier` مع وصول لا يفرض استدعاءات static عامة خارج نمط scopes الحالي.
5. توفير API للاشتراك المحدد بمفاتيح أو مقارنة أثر التغيير، كي لا يعاد بناء كل Workbench عند أي قيمة.
6. ترتيب التخلص من الخدمة والمستمعات والمخازن في `State.dispose`.
7. إضافة اختبارات للتحديث الفوري، الأحداث، إعادة التهيئة، وفشل تحميل المخزن.

**معيار القبول**

- يتم إنشاء الخدمة مرة واحدة لكل التطبيق ويجري التخلص منها مرة واحدة.
- تحصل أجزاء التطبيق على القيمة نفسها عبر الخدمة ولا تنشئ مخازن مستقلة.
- فشل التهيئة لا ينتج مظهراً مضللاً؛ تظهر حالة تحميل/خطأ محددة أو افتراضات آمنة موثقة.

**الاعتماد:** المرحلتان 2 و3.

### المرحلة 5: واجهة Settings أولية قابلة للاستخدام

**الهدف:** تمكين المستخدم من اكتشاف وتعديل الإعدادات المعرفة، قبل توسيع نطاق التخزين إلى Workspace.

**المهام**

1. إضافة شاشة Settings في بنية Workbench وربط مدخلها بعنصر Settings في Activity Bar/وسيلة التنقل الحالية.
2. عرض الإعدادات حسب الفئات من metadata في registry، لا باستخدام قوائم مستقلة مكررة داخل كل صفحة.
3. توفير بحث نصي محلي بالمفتاح والوصف والفئة، وتصفية بحسب الفئة.
4. اختيار control حسب النوع: Switch للـ bool، Slider/حقل مضبوط للأرقام، TextField للنصوص، Dropdown/SegmentedButton للقيم المحدودة.
5. توضيح القيمة الافتراضية ومصدر القيمة الحالية، وإظهار validation inline.
6. إظهار مؤشر حفظ/خطأ عند الكتابة غير المتزامنة. لا يُعلن نجاح دائم قبل اكتمال التخزين.
7. إضافة Reset لإزالة override من الهدف الحالي والعودة إلى المصدر الأدنى، بدلاً من تخزين نسخة من القيمة الافتراضية.
8. كتابة اختبارات Widget للبحث، التعديل، reset، عرض المصدر، حالات التحميل والخطأ، وإتاحة الوصول الأساسية.

**مخرجات مقترحة**

- `lib/parts/settings/settings_screen.dart`
- Widgets مشتركة لعناصر الإعدادات بحسب النوع.
- اختبارات ضمن `test/settings/`.

**معيار القبول**

- يمكن للمستخدم تعديل إعداد وتجده محفوظاً بعد إعادة تشغيل التطبيق.
- يظهر إعداد غير صالح أو فشل حفظ برسالة مفهومة ولا يُبتلع.
- تستخدم الشاشة definitions نفسها التي يستهلكها runtime.

**الاعتماد:** المرحلة 4. يمكن بناء هيكل واجهة أولي بالتوازي مع المرحلة 3، لكن ربط الحفظ ينتظر الخدمة.

### المرحلة 6: نقل المزايا الحالية تدريجياً إلى الخدمة

**الهدف:** جعل إعدادات التطبيق الفعلية مستهلكة للنظام المركزي دون تغيير المظهر الافتراضي أو كسر الاختبارات.

**المهام**

1. **Status Bar:** تحويل `StatusBarService` ليقرأ `statusBar.hiddenEntryIds` من `SettingsService`، ثم إزالة التخزين المكرر من الخدمة بعد اكتمال ترحيل البيانات. حافظ على عقد التخزين الحالي مؤقتاً عبر adapter إن كان ذلك يقلل مخاطر التغيير.
2. **Theme:** استبدال `const darkModern` الثابت في bootstrap باختيار theme معرف في الكتالوج، وتوفير resolver يحول قيمة theme id إلى `EditorThemeData`. احتفظ بـ `darkModern` كافتراضي مطابق تماماً للسلوك الحالي.
3. **Layout:** استهلاك الإعدادات الدائمة للأجزاء المرئية/الأبعاد عند التهيئة. لا تحفظ الحالات المؤقتة أو تركيبات Zen Mode تلقائياً ضمن إعدادات المستخدم من دون قرار منتج واضح.
4. **Terminal:** تحميل القيم الافتراضية من الكتالوج وتطبيق التغييرات على `TerminalConfigService` مع إشعار المستهلكين وإعادة حساب قياس الخط عند اللزوم.
5. إزالة الأرقام والنصوص الافتراضية المكررة من الخدمات بعد نقلها، مع بقاء القيم المرجعية في registry فقط.
6. توفير اختبارات تكامل لكل مجال، والتحقق من عدم وجود loop بين تغيير الخدمة وإعادة كتابة الإعداد.

**ترتيب فرعي موصى به:** Status Bar أولاً لأنه يملك بالفعل مخزناً وتغطية؛ ثم Theme وTerminal؛ ثم Layout لأنه يتقاطع مع Zen Mode وحالة الواجهة.

**معيار القبول**

- أول تشغيل بعد التغيير يطابق الثيم والتخطيط والسلوك السابقين.
- تغيير إعداد في Settings ينعكس فوراً على الميزة المعنية.
- إعادة التشغيل تحفظ الإعدادات المسموح بحفظها فقط.
- بيانات Status Bar السابقة تبقى بعد الترحيل.

**الاعتماد:** المرحلتان 4 و5. يمكن تنفيذ المجالات الفرعية بشكل مستقل بعد اكتمال الخدمة.

### المرحلة 7: إعدادات Workspace وملف `.vscode/settings.json`

**الهدف:** السماح للمشروع المفتوح بتجاوز بعض إعدادات المستخدم، على غرار إعدادات مساحة العمل في VS Code.

**المهام**

1. إنشاء `WorkspaceSettingsStore` يعتمد مسار Workspace النشط من `FileExplorerController.workspacePath`.
2. قراءة/كتابة `.vscode/settings.json` داخل جذر Workspace. لا تنشئ أو تعدّل الملف عند مجرد القراءة؛ الإنشاء يحدث عند أول تغيير فقط.
3. استخدام parser/encoder JSON موثوق مع تنسيق ثابت. عند JSON غير صالح، احتفظ بالمحتوى ولا تستبدله بصمت؛ اعرض خطأ يوفر فتح الملف أو تصحيحه يدوياً.
4. منع Path traversal: يجب اشتقاق المورد من جذر Workspace والتحقق أن المسار الناتج يقع تحته، مع مراعاة فواصل المسارات في المنصات المدعومة.
5. مراقبة تغييرات الملف الخارجية وإعادة تحميل القيم، مع منع loop بين الكتابة المحلية وحدث watcher.
6. تحديد مجموعة الإعدادات القابلة لـ Workspace في registry. في الإصدار الأول، استبعد مفاتيح الأمان والتنفيذ/المسارات الحساسة حتى توجد سياسة ثقة واضحة.
7. عند تغيير workspace، إعادة بناء السياق والقيم الفعالة وإشعار المستهلكين؛ لا تسرب تفضيلات مجلد سابق إلى مجلد جديد.
8. في Settings UI، إضافة اختيار هدف `User`/`Workspace` للإعدادات التي تسمح بالنطاقين، وعرض القيمتين ومصدر الفعالة.
9. مراجعة تأثير استثناء `.vscode` الحالي في [FileSystemService](../lib/core/file_system/services/file_system_service.dart). لا يلزم عرضه في شجرة الملفات لتنفيذ التخزين، لكن يجب ألا يتعارض ذلك مع اختيار المستخدم لفتح الملف أو إدارة الإعدادات.
10. اختبار مجلد إعداداته غير موجود، ملف تالف، تغيير خارجي، مسار Workspace يتغير، رفض مفتاح user-only، وفشل صلاحيات الكتابة.

**معيار القبول**

- تتغلب قيمة Workspace على قيمة المستخدم للمفاتيح المسموح بها فقط.
- لا تُكتب إعدادات Workspace خارج جذر المجلد المفتوح.
- يظل الملف التالف محفوظاً دون overwrite تلقائي.
- تغيير Workspace يعيد الحساب ويزيل أي قيمة فعالة تخص Workspace السابق.

**الاعتماد:** المرحلة 2 والبنية الأساسية من المرحلة 4. يمكن تطوير التخزين بالتوازي مع ربط مراحل 5-6، لكن واجهة تحديد الهدف تعتمد وجود resolver.

### المرحلة 8: تحسينات البحث، المراجعة، والتوافق

**الهدف:** إتمام جودة النظام وتجهيزه للتوسع دون إضافة أنظمة غير مطلوبة.

**المهام**

1. إكمال البحث مع دعم صيغ بسيطة مثل `key:`, `category:`, و`modified` إذا كان مفيداً؛ لا تضف لغة استعلام معقدة مبكراً.
2. إضافة فرز واضح، مفاتيح إعدادات قابلة للنسخ، ووصول من لوحة المفاتيح ودلالات وصول مناسبة.
3. توفير أمر إعادة ضبط إعدادات المستخدم أو Workspace، مع تأكيد واضح ونطاق محدد للعملية.
4. إضافة سجل تغييرات/تشخيص dev-only يعرض المفتاح ومصدره من دون كشف محتوى حساس أو تسجيل قيم سرية.
5. مراجعة الأداء: caching للقيم الفعالة فقط عند وجود قياس يبرر ذلك، وعدم إعادة بناء كل Settings UI لكل حدث.
6. إضافة اختبارات regression تغطي تحويل القيم القديمة ومخططات JSON والفشل والتنافس على الكتابة.
7. تحديث وثائق المطور والمستخدم عند الانتهاء من السلوك الفعلي، لا قبل ثباته.

**معيار القبول**

- مسار البحث والتنقل والتعديل وإعادة الضبط يعمل بالكامل بلوحة المفاتيح.
- لا توجد عمليات كتابة صامتة أو fallback يخفي أخطاء البيانات.
- كل خصائص الإصدار الأول موثقة ومختبرة من مصدرها حتى واجهتها.

**الاعتماد:** المراحل 5-7.

### المرحلة 9: امتدادات مستقبلية اختيارية

لا تبدأ هذه المرحلة ضمن الإصدار الأول. تنفذ فقط عند وجود طلب منتج واضح:

- **Overrides حسب اللغة:** إضافة سياق `languageId`، نطاق `languageOverridable`، مخزن overrides وطريقة دمجها بعد القيمة الأساسية، مع اختبارات تخص اللغة المحللة للمستند.
- **ملفات تعريف المستخدم:** فصل مخزن المستخدم بحسب profile id، وتحديد التبديل والمزامنة بين الملفات.
- **مساهمة وحدات/Plugins:** تسجيل definitions من وحدات داخل التطبيق مع مالك/namespace، تحقق من التعارض، وإزالة آمنة عند إلغاء الوحدة.
- **سياسة إدارية أو إعدادات مُدارة:** طبقة غير قابلة للكتابة من Settings UI، مع أولوية وسياسة فحص صريحة.
- **استيراد/تصدير ومزامنة:** صيغة نسخة schema versioned، كشف التعارضات، واستثناء المفاتيح المحلية/الحساسة.

لا تضف امتداداً عاماً أو مزامنة بعيدة قبل تثبيت عقود مصادر القراءة والكتابة ومعايير الأمان.

## 7. خريطة الاعتمادات وقابلية استقلال المراحل

```text
0 خط الأساس
  -> 1 سجل وتعريفات
  -> 2 resolver ونموذج المصادر
  -> 3 مخزن المستخدم والترحيل
  -> 4 الخدمة وحقنها
  -> 5 واجهة Settings
  -> 6 نقل المزايا الحالية

2 + 4
  -> 7 إعدادات Workspace

5 + 6 + 7
  -> 8 التحسينات وضمان الجودة
  -> 9 التوسعات الاختيارية
```

المراحل 5 و6 قابلتان للتوازي جزئياً بعد توفر الخدمة: يمكن لفريق الواجهة بناء صفحة الإعدادات بينما ينقل مجال مستقل إعداداته إلى الكتالوج. أما Workspace فيمكن إعداد مخزنه بعد المرحلة 2، لكن لا يدمج قبل أن تكون دورة الخدمة والأحداث مستقرة. كل مرحلة يجب أن تنتهي بحالة قابلة للاستخدام والاختبار، لا بفرع معماري غير موصول.

## 8. استراتيجية الاختبارات والتحقق

### اختبارات الوحدات

- سجل التعريفات: keys مكررة، أنواع، افتراضيات، validators، enums.
- resolver: الأولوية، مصادر مفقودة، النطاق، inspect، وتغير القيم الفعالة.
- مخازن البيانات: قراءة/كتابة/ترحيل/بيانات تالفة/أخطاء.
- الخدمة: التهيئة، update، الحدث، التصفية حسب المفتاح، dispose، والكتابات المتتابعة.

### اختبارات Widgets والتكامل

- عناصر Settings لكل نوع، التحقق، البحث، reset، اختيار الهدف، وحالات فشل الحفظ.
- SettingsScope مع استهلاك قيمة تتغير أثناء الجلسة.
- تغيّر الثيم والتخطيط والطرفية وشريط الحالة دون إعادة تشغيل.
- أولوية Workspace والتحول بين مساحتين وعدم تسرب الإعدادات.
- مراقبة تغييرات `.vscode/settings.json` من خارج التطبيق ومعالجة الملف غير الصالح.

### أوامر تحقق مقترحة

بعد كل مرحلة، شغّل أصغر مجموعة مناسبة:

```bash
flutter test test/settings
flutter test test/statusbar
flutter test test/widget_test.dart
flutter analyze
```

لا تشغّل كل الاختبارات بعد كل تعديل صغير. عند تغيير التخزين أو bootstrap أو مخطط النطاقات، شغّل مجموعة الاختبارات ذات الصلة ثم `flutter analyze`. اختبارات الوثائق وحدها لا تتطلب build.

## 9. مخاطر وطرق الحد منها

| الخطر | المعالجة |
| --- | --- |
| فقد تفضيلات Status Bar القديمة | ترحيل idempotent، والاحتفاظ بالمفتاح القديم حتى نجاح الكتابة والتحقق. |
| بناء abstraction أكبر من حاجة المشروع | دعم مصادر ثلاثة فقط أولاً، وتأجيل profiles والسياسات والإضافات. |
| تغير السلوك الافتراضي أثناء النقل | تسجيل القيم الحالية واختبارات regression قبل ربط المستهلكين. |
| تلف أو JSON غير صالح في Workspace | عدم overwrite، إظهار خطأ، وتوفير طريقة فتح/تصحيح الملف. |
| سباق الكتابة أو أحداث watcher المتكررة | طابور كتابة/مقارنة محتوى، ومنع إعادة تحميل ناتج الكتابة المحلية مرتين. |
| تسرب إعدادات Workspace السابق | تضمين workspace identity في السياق ومحو cache عند تبديل الجذر. |
| إعدادات Workspace غير موثوقة | قائمة مفاتيح مسموحة؛ تأجيل الإعدادات التنفيذية إلى وجود Workspace Trust. |
| إعادة بناء واجهة التطبيق كلها | اشتراك بالمفاتيح التي تعتمد عليها كل ميزة، وعدم الاعتماد على notifier شامل بلا داعٍ. |
| الاعتماد على SharedPreferences لكل شيء | إبقاؤه لمخزن المستخدم فقط؛ إعدادات Workspace تكتب داخل مجلد المشروع. |

## 10. تعريف الاكتمال

يعد الإصدار الأساسي مكتملاً عندما:

- توجد definitions typed لكل مفاتيح الإعداد المعتمدة، ولا توجد قيم افتراضية متكررة بين UI والخدمات.
- تعمل القراءة والكتابة والفحص من `SettingsService` مع مصدر قيمة واضح.
- واجهة Settings تعدل وتعيد ضبط الإعدادات وتعرض فشل الحفظ بوضوح.
- إعدادات Status Bar الحالية تهاجر دون فقد، وتستهلك الخدمة العامة.
- اختيار الثيم وإعدادات الطرفية/التخطيط التي تم تحديدها تتغير وقت التشغيل وتستمر عبر إعادة التشغيل.
- إعدادات Workspace تعمل بالمفاتيح والنطاقات المسموح بها، إذا كان ذلك ضمن إصدار التسليم المتفق عليه.
- اختبارات المصادر والتخزين والواجهة والتكامل والتحليل الساكن تمر، ولا توجد تغييرات جانبية على محرر النصوص أو LSP.
- تظل الميزات غير المستهدفة (Zen Mode المؤقت، حالة المؤشر، التبويبات المفتوحة) خارج التخزين ما لم يصدر قرار تصميم مستقل.

## 11. ترتيب تنفيذ موصى به

ابدأ بالمرحلة 0 ثم 1 و2 لاختبار قرارات النطاق والأولوية قبل كتابة واجهة. بعد ذلك أنجز مخزن المستخدم وترحيل Status Bar في المرحلة 3، ثم اربط الخدمة بـ bootstrap. عندها يمكن تسليم واجهة Settings أولية، ونقل مجالات الثيم والطرفية والتخطيط كمهام منفصلة. أخيراً أضف Workspace JSON بعد تثبيت المسارات وتبديل Workspace، ثم نفذ التحسينات.

هذا الترتيب يقلل مخاطر الانتقال الشامل دفعة واحدة، ويسمح بتسليم أجزاء مفيدة مبكراً مع وجود اختبارات لكل طبقة.
