# الخطة التنفيذية لبناء نظام خادم اللغة (LSP) ومحرك تنفيذ الأكواد

> **مرجع الخطة:** مستندة بالكامل إلى التحليل المعماري لـ VS Code في  
> [`docs/vscode_lsp_and_code_execution_architecture.md`](file:///home/osm/flutter_projects/code_editor/docs/vscode_lsp_and_code_execution_architecture.md)  
> **الهدف:** بناء عميل بروتوكول خادم لغة (LSP Client) متكامل ومرن ومستقل عن أي لغة محددة (Language-Agnostic)، بجانب محرك مستقل لتشغيل وتنفيذ الأكواد، مدمجين بسلاسة في محرر الأكواد المبني بـ Flutter (`code_editor`).

---

## 🧭 الرؤية والمبادئ المعمارية الحاكمة

1. **العزل التام للمهام (Separation of Concerns):**
   - **محرك LSP:** مسؤول حصرياً عن التحليل، الإكمال التلقائي، اكتشاف الأخطاء، والانتقال للتعريف. لا يتدخل في تشغيل أو ترجمة الأكواد.
   - **محرك التنفيذ (Execution Service):** مسؤول عن إطلاق العمليات الحقيقية، مراقبة الخرج (`stdout`/`stderr`)، وإدارتها من اللوحة السفلية (`PanelWidget`).
2. **عدم حظر واجهة المستخدم (Zero UI Freezes):**
   - جميع عمليات قراءة وكتابة الـ `stdio`، والتحليل، وفك تشفير JSON تتم عبر `Streams` و `Asynchronous I/O` لتأكيد بقاء واجهة المحرر بمعدل 60+ إطار في الثانية دائماً.
3. **دعم أي لغة برمجية (Language-Agnostic Registry):**
   - تصميم واجهات عامة (Generic Client) تسمح بتوصيل أي خادم LSP خارجي (`dart language-server`, `pyright`, `rust-analyzer`, `gopls`, `clangd`) بمجرد توفير أمر التشغيل وامتداد الملفات.
4. **تكامل متسق مع واجهة المحرر القائمة:**
   - ربط الأخطاء التلقائية بلوحة المشاكل في [panel_widget.dart](file:///home/osm/flutter_projects/code_editor/lib/parts/panel/panel_widget.dart) وبالخطوط المتعرجة في المحرر.
   - ربط مخرجات البرامج بتبويب `Output` أو `Terminal` في اللوحة السفلية.

### 🟢 المرحلة 1: طبقة النقل والتأطير (Transport & Framing Layer)

#### 1. الهدف

بناء الأساس الشبكي ومنخفض المستوى للتخاطب مع أي خادم لغة عبر قنوات الدخل والخرج القياسية (`stdio`)، وضمان فك تشفير الرسائل بدقة دون فقدان بايتات حتى عند تجزؤ الحزم عبر الشبكة أو النظام.

#### 2. المهام التنفيذية

- [x] **1.1. تنفيذ مُشفّر وفك مُشفّر التأطير (`LspFraming`):**
  - بناء محرك قراءة يعتمد على تجميع البايتات (`BytesBuilder` أو `StringBuffer`).
  - التحقق الصارم من ترويسات `Content-Length: <number>\r\n\r\n`.
  - معالجة الحالات الحدية:
    - وصول الرسالة على أجزاء متعددة (Fragmentation).
    - وصول رسالتين أو أكثر في نفس الحزمة الواحدة (Batching).
    - دعم الرموز غير اللاتينية عبر فك التشفير القياسي `utf8.decode`.
- [x] **1.2. بناء قناة العملية منخفضة المستوى (`LspProcessChannel`):**
  - استدعاء `Process.start(command, args)` لإطلاق خادم اللغة في الخلفية كعملية معزولة.
  - الاستماع لتيار `stdout` وتوجيهه إلى `LspFraming.decodeChunk`.
  - الاستماع لتيار `stderr` لتسجيل أخطاء خادم اللغة الداخلية وتوجيهها لـ Logger المحرر.
  - إرسال الرسائل عبر تيار `stdin` باستخدام `LspFraming.encode`.
- [x] **1.3. إدارة الإنهاء القسري وحماية العمليات اليتيمة (Process Cleanup):**
  - ضمان قتل عملية خادم اللغة تلقائياً عند إغلاق محرر Flutter أو تعطل التطبيق (`ProcessSignal.sigterm`).

#### 3. مخرجات المرحلة والمعايير

- وحدة `lsp_framing_test.dart` تختبر بنجاح إرسال واستقبال 10,000 رسالة مقطعة بسرعة فائقة دون خطأ فك تشفير واحد.

### 🟢 المرحلة 2: دورة حياة البروتوكول والتهيئة (Lifecycle & Handshake)

#### 1. الهدف

تطبيق معايير JSON-RPC 2.0، إدارة معرفات الطلبات الفريدة، وإتمام بروتوكول المصافحة الأولي مع الخادم بنجاح.

#### 2. المهام التنفيذية

- [x] **2.1. تصميم كائنات الرسائل (`LspMessage`):**
  - `LspRequest`: يحتوي على `jsonrpc: "2.0"`, `id: int`, `method: String`, `params: dynamic`.
  - `LspResponse`: يحتوي على `id: int`, `result: dynamic`, `error: LspResponseError?`.
  - `LspNotification`: رسائل أحادية الاتجاه بدون `id` وبدون انتظار رد.
- [x] **2.2. مدير مطابقة الطلبات (`LspRequestManager`):**
  - إنشاء جدول داخلي للطلبات المعلقة: `Map<int, Completer<dynamic>> _pendingRequests`.
  - توليد معرّف تسلسلي متزايد آمن لكل طلب جديد (`_nextRequestId++`).
  - وضع مهلة زمنية ذكية (Timeout) لأي طلب يتأخر فيه رد الخادم (مثلاً 5 إلى 10 ثوانٍ) لمنع تعليق التطبيق.
- [x] **2.3. تنفيذ مصافحة التهيئة (`initialize` Handshake):**
  - إرسال طلب `initialize` يحتوي على:
    - قدرات العميل الأساسية (`clientCapabilities`: دعم المزامنة، الإكمال، التوثيق، التشخيصات).
    - مسار مساحة العمل الحالية (`rootUri`).
  - حفظ الرد `InitializeResult` واستخراج قدرات الخادم (`serverCapabilities`).
  - إرسال إشعار التأكيد `initialized`.
- [x] **2.4. تنفيذ دورة الإغلاق النظيف (`shutdown` و `exit`):**
  - إرسال طلب `shutdown` عند إغلاق المشروع.
  - إرسال إشعار `exit` بعد تلقي رد الـ shutdown، ثم إغلاق قنوات الاتصال والعملية.

#### 3. مخرجات المرحلة والمعايير

- الاتصال بخادم حقيقي (مثل `dart language-server --protocol=lsp`)، وطباعة `serverCapabilities` بنجاح في السجلات، وإغلاقه بشكل نظيف بدون بقاء العملية معلقة في النظام.

### 🟢 المرحلة 3: مزامنة المستندات وإلغاء الطلبات (Document Sync & Cancellation)

#### 1. الهدف

إخبار خادم اللغة بكل عملية فتح أو تعديل أو حفظ أو إغلاق للملفات في المحرر، لإبقاء شجرة التحليل (AST) لدى الخادم متطابقة دائماً مع ما يراه المستخدم على الشاشة.

#### 2. المهام التنفيذية

- [x] **3.1. متتبع حالة المستندات (`LspDocumentTracker`):**
  - تخزين قائمة الملفات المفتوحة مع أرقام إصداراتها: `Map<String, int> _documentVersions`.
  - زيادة رقم الإصدار (`version++`) مع كل تعديل يطرأ على الملف.
- [x] **3.2. إرسال أحداث دورة حياة المستند:**
  - `textDocument/didOpen`: إرسال المحتوى الكامل عند فتح التبويب لأول مرة.
  - `textDocument/didClose`: إشعار الخادم لإلغاء الملف من الذاكرة عند إغلاق التبويب بالمحرر.
  - `textDocument/didSave`: إشعار الخادم عند حفظ الملف يدوياً أو تلقائياً.
- [x] **3.3. تطبيق المزامنة النصية (Text Synchronization):**
  - **الخطوة الأولى (المزامنة الكاملة - Full Sync):** إرسال النص كاملاً داخل `textDocument/didChange`.
  - **مؤقت تأخير التغييرات (Debouncing):** عدم إرسال `didChange` مع كل حرف يُكتب مباشرة، بل تجميعها وتمريرها بعد توقف المستخدم عن الكتابة لمدة (مثلاً 150-250ms) لتفادي إرهاق معالج الجهاز.
  - **الخطوة المتقدمة (المزامنة التزايدية - Incremental Sync):** إرسال التعديل الجزئي (`range` و `text`) إذا أعلن الخادم دعمه لذلك في قدراته (`TextDocumentSyncKind.Incremental`).
- [x] **3.4. دعم إلغاء الطلبات غير المرغوبة (`$/cancelRequest`):**
  - عند قيام المستخدم بالكتابة بسرعة بينما ينتظر المحرر نتائج إكمال سابقة، يتم إرسال `$/cancelRequest` بالمعرف القديم لتحرير موارد الخادم فوراً.

### 🟢 المرحلة 4: نظام التشخيصات وتظليل الأخطاء (Diagnostics & Problems System)

#### 1. الهدف

استقبال الأخطاء والتحذيرات اللحظية من خادم اللغة وعرضها للمستخدم بشكل مرئي جذاب في المحرر وداخل اللوحة السفلية.

#### 2. المهام التنفيذية

- [x] **4.1. التقاط إشعار التشخيصات (`textDocument/publishDiagnostics`):**
  - استماع عميل LSP للإشعار غير المتزامن وتحويل عناصر الـ JSON إلى كائنات Dart:

    ```dart
    class DiagnosticItem {
      final String uri;
      final LspRange range;
      final DiagnosticSeverity severity; // Error, Warning, Information, Hint
      final String message;
      final String? source;
      final String? code;
    }
    ```

- [x] **4.2. إدارة مخزن المشاكل المركزي (`DiagnosticsService`):**
  - تحديث قائمة الأخطاء لكل ملف: `Map<String, List<DiagnosticItem>>`.
  - حساب إجمالي الأخطاء والتحذيرات لربطه بشريط الحالة (`StatusBar`) وشريط اللوحة السفلية (`Panel Tab Badge`).
- [x] **4.3. ربط المشاكل باللوحة السفلية (`ProblemsView` في `panel_widget.dart`):**
  - بناء ويدجت `ProblemsView` لعرض المشاكل مقسمة حسب الملفات، مع أيقونة معبرة عن درجة الخطورة (أحمر للخطأ، أصفر للتحذير).
  - عند النقر على أي مشكلة في اللوحة، يتم تركيز المحرر والانتقال إلى السطر والعمود المحددين تلقائياً.
- [x] **4.4. رسم الخطوط ومؤشرات الأخطاء في المحرر:**
  - إمداد شريط الأرقام (Gutter) بمؤشرات الأخطاء والتحذيرات اللحظية لكل سطر.

  - عند نقر المستخدم على زر CodeLens `Run`، يقوم المحرر بتوجيه الأمر مباشرة إلى **محرك تنفيذ الكود** (`ExecutionController`)، وتمرير اسم الملف والدالة المطلوب تشغيلها وتبديل اللوحة السفلية لتبويب `OUTPUT`.

### 🟢 المرحلة 7: محرك تشغيل وتنفيذ الأكواد المستقل (Independent Execution Subsystem)

#### 1. الهدف

بناء نظام تشغيل حقيقي مستقل قادر على إطلاق الأكواد ومتابعتها وإيقافها، وعرض النتائج بشكل تفاعلي داخل اللوحة السفلية.

#### 2. المهام التنفيذية

- [x] **7.1. مشغل العمليات المستقل (`ProcessRunner`):**
  - تنفيذ الأوامر عبر `Process.start` مع دعم تمرير مسار العمل (`workingDirectory`).
  - التقاط الخرج القياسي (`stdout`) وخرج الأخطاء (`stderr`) كتيارات منفصلة وتمريرها لمتحكم المخرجات.
- [x] **7.2. إدارة جلسة التنفيذ (`ExecutionSession`):**
  - تتبع حالة الجلسة: `Idle`, `Running`, `Completed`, `Failed`, `TerminatedByUser`.
  - توفير زر لإيقاف العملية قسراً (Stop / Kill Process عبر `Process.kill`).
- [x] **7.3. بناء شاشة مخرجات التنفيذ (`ExecutionOutputView`):**
  - إضافة تبويب `Output` داخل [panel_widget.dart](file:///home/osm/flutter_projects/code_editor/lib/parts/panel/panel_widget.dart).

  - دعم تمييز الألوان الأساسي لمخرجات الأخطاء وتأطير وقت بداية ونهاية العملية ورمز الخروج (`Exit Code`).
- [x] **7.4. زر التشغيل السريع في شريط الأدوات (Run Action):**
  - وضع زر `Run` في شريط التبويبات بالمحرر لتشغيل الملف النشط حالياً ومتابعة خرجه فوراً.

### 🟢 المرحلة 8: اختبارات الجودة والاستقرار والأداء (Testing & Hardening)

#### 1. الهدف

التحقق من صلابة النظام تحت أعباء العمل البرمجية الكبيرة، وضمان عدم وجود تسريبات في الذاكرة (Memory Leaks) أو عمليات معلقة.

#### 2. المهام التنفيذية

- [x] **8.1. اختبارات الوحدة المعزولة (Unit Testing):**
  - فحص محرك التأطير `LspFraming` مع سيناريوهات الحزم المشوهة والمجزأة والضغط العالي (2,000 رسالة مقطعة).
  - اختبار معالجة مطابقة الطلبات بالردود وتخطي الـ Timeouts في `LspRequestManager` و `LspClient`.
- [x] **8.2. الاختبار التكاملي ومحرك التنفيذ (Integration & Execution Testing):**
  - اختبار تشغيل الأوامر والتقاط `stdout` و `stderr` والتعامل مع رموز الخروج وإيقاف العمليات في `ExecutionController`.
- [x] **8.3. فحص الأداء وتفادي التسريبات (Resource Management):**
  - إغلاق كافة التيارات والمؤقتات في `dispose` واجتياز اختبارات واجهة المستخدم (Widget Smoke Tests) بنجاح 100%.

## 🎯 نقطة الانطلاق الفورية الموصى بها

للبدء العملي الآن، يوصى بالانطلاق في **المرحلة 1**:

1. إنشاء مجلد `lib/core/lsp/connection/`
2. كتابة واختبار وحدة `LspFraming` لفك وترميز ترويسات بروتوكول `Content-Length`.
3. كتابة مشغل العملية `LspProcessChannel` لتأكيد نجاح إطلاق وتدفق بيانات خادم اللغة التجريبي الأول.
