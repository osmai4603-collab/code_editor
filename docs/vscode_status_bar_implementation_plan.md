# خطة تنفيذية: معمارية Status Bar في محرر Flutter

> **المرجع المعماري:** [تحليل شريط الحالة في VS Code](./vscode_status_bar_architecture_analysis.md)  
> **المشروع المستهدف:** `code_editor`  
> **الهدف:** استبدال عناصر الحالة الثابتة الحالية بنظام Status Bar قابل للتوسع، مرتبط بحالة المحرر، قابل للإخفاء والتخصيص، ويحافظ على بساطة المشروع الحالي.

---

## 1. هدف الخطة ومبادئ التنفيذ

تحدد هذه الوثيقة عملاً قابلاً للتنفيذ على مراحل متتابعة. كل مرحلة لها مخرجات واختبارات وشروط قبول، ويمكن اعتبارها نقطة مراجعة قبل بدء المرحلة التالية.

المبادئ:

1. فصل مصدر الحالة عن عرضها: المحرر أو خدمة التشخيص تنتج الحالة، ومساهمة مستقلة تحولها إلى عنصر، والشريط يعرض العناصر.
2. عدم ربط `StatusBarWidget` مباشرة بكل ميزة؛ يستهلك الشريط عقداً عاماً للعناصر.
3. استخدام نموذج Dart صريح وواجهات typed بدلاً من خرائط خصائص غير محددة النوع.
4. استخدام `ChangeNotifier` و`InheritedNotifier` الموجودين بالفعل في المشروع، من دون إدخال حزمة إدارة حالة جديدة.
5. عدم إنشاء نظام إضافات أو بنية نوافذ متعددة تحاكي VS Code؛ المشروع الحالي تطبيق Flutter بنافذة Workbench واحدة. يوفّر النظام داخلياً عقد مساهمات قابلاً للتوسع فقط.
6. المحافظة على الارتفاع الحالي 22px، وعلى ظهور الشريط الحالي افتراضياً.
7. ربط الأوامر بسلوك فعلي ومتاح؛ لا تترك عناصر تفاعلية ذات `onTap` فارغ.
8. عدم عرض معلومات تخمينية على أنها حقيقة: الترميز ونهاية السطر ومعلومات SCM تظهر فقط عندما يكون مصدرها موثوقاً وموجوداً.

## 2. الحالة الحالية في المشروع

### موجود

- [statusbar_widget.dart](../lib/parts/statusbar/statusbar_widget.dart): واجهة واحدة ثابتة بعناصر مكتوبة داخل `Row`، تشمل الفرع، المشكلات، موضع المحرر، المسافات، UTF-8، LF، اللغة والإشعارات. معظم إجراءات النقر فارغة.
- [workbench_scaffold.dart](../lib/layout/widgets/workbench_scaffold.dart): يضع الشريط أسفل Workbench، ويخفيه إذا كانت `isStatusBarVisible` أو إذا كان Zen Mode مفعلاً.
- [layout_state.dart](../lib/layout/models/layout_state.dart): يتضمن `isStatusBarVisible` ويفعّل ظهوره افتراضياً.
- [layout_controller.dart](../lib/layout/controllers/layout_controller.dart): يدير حالة التخطيط، لكن لا يوفر حالياً أمراً لتبديل ظهور الشريط.
- [editor_theme.dart](../lib/core/theme/editor_theme.dart): يحتوي ألوان الخلفية والنص والـ hover الأساسية للشريط.
- [editor_controller.dart](../lib/layout/controllers/editor_controller.dart): يتيح الوصول إلى التبويب النشط واللغة والمسار والمحتوى وحالة الحفظ.
- [diagnostics_service.dart](../lib/core/lsp/diagnostics/diagnostics_service.dart): يتيح إجماليات الأخطاء والتحذيرات ومشكلات الملف.
- [code_editor_controller.dart](../lib/parts/editor/controllers/code_editor_controller.dart): يرث من `TextEditingController` ويملك النص والاختيار، لكن حالة المؤشر غير منشورة إلى الشريط.
- [main.dart](../lib/main.dart): يهيئ الخدمات والـ scopes الحالية؛ لا يوجد StatusBarService مستقل بعد.
- [editor_constants.dart](../lib/core/constants/editor_constants.dart): يحدد ارتفاع الشريط الحالي 22px.

### غير موجود بعد

- نموذج entry وعقد للإضافة والتحديث والتخلص.
- خدمة/متحكم لإدارة مساهمات الشريط وترتيبها.
- نموذج عرض مستقل مع الأولوية والمحاذاة والعناصر المخفية.
- مصدر حالة موحد لموضع المؤشر.
- قائمة إدارة عناصر الشريط والتخزين الدائم لتفضيلات إخفائها.
- اختبارات مخصصة للنموذج، الخدمة، واجهة العنصر، والتكامل.
- بيانات فعلية للفرع وUTF-8/LF والإشعارات، وواجهة عامة للإضافات.

## 3. النطاق المستهدف

### الإصدار الأساسي المطلوب

- شريط سفلي بعقد موحد لإضافة وتحديث وإزالة العناصر.
- مجموعتا محاذاة يسار ويمين، وترتيب عددي ثابت، مع دعم التموضع النسبي البسيط عند الحاجة.
- تحديث العناصر بكفاءة عبر accessor، ومعالجة صحيحة لدورة حياة listeners.
- ربط العناصر الموجودة فعلياً بالمشروع: التشخيصات، التبويب النشط/اللغة، وموقع المؤشر.
- تلميحات، أيقونات، أوامر نقر حقيقية، دلالات وصول، وأنواع لونية أساسية.
- إخفاء عنصر منفرد واستعادة الاختيار بعد إعادة تشغيل التطبيق.
- تبديل ظهور الشريط وإبقاؤه متوافقاً مع Zen Mode والتخطيط الحالي.
- التعامل مع عرض الشاشة المحدود دون overflow غير معالج.

### خارج النطاق في الإصدار الأساسي

- تنفيذ واجهة VS Code extension host أو بروتوكول RPC.
- نوافذ Workbench مساعدة متعددة.
- SCM فعلي، نظام إشعارات، ملف تعريف workspace، أو محوّل ترميز/نهاية سطر ما لم تُبنَ مصادرها أولاً.
- محتوى HTML مخصص أو أدوات hover غنية مع أوامر متعددة.
- محرر إعدادات عام لإعادة ترتيب العناصر بالسحب.

يمكن إضافة هذه القدرات لاحقاً كمساهمات جديدة من دون تعديل جوهر العرض.

## 4. المعمارية المستهدفة للمشروع

```text
مصادر الحالة
├── EditorDocumentsController ── التبويب النشط، اللغة، الملف، dirty state
├── EditorStatusController ──── موضع السطر/العمود وحالة التركيز/التحديد
└── DiagnosticsService ──────── أعداد الأخطاء والتحذيرات
             │
             ▼
Status bar contributions (مساهمات مستقلة)
├── EditorContextStatusContribution
├── DiagnosticsStatusContribution
└── لاحقاً: SCM / Encoding / EOL / Notifications
             │ add/update/dispose
             ▼
StatusBarService + StatusBarViewModel
├── ترتيب ومحاذاة ورؤية العناصر
├── حفظ تفضيلات الإخفاء
└── أحداث تغيّر العناصر
             │
             ▼
StatusBarWidget
├── StatusBarItemWidget
├── Left items / Right items
└── القائمة، الوصول، التلميحات والتفاعل
```

يبقى `WorkbenchScaffold` مسؤولاً عن موضع الشريط وإخفائه كجزء من تخطيط النافذة. تتولى خدمة الحالة إدارة **العناصر داخل الشريط**؛ لا تخلط بين ظهور الجزء وظهور عنصر بعينه.

## المرحلة 0: حسم العقد والنطاق الوظيفي

**الهدف:** منع بناء عناصر عامة أو سلوكيات غير قابلة للتنفيذ قبل الاتفاق على مصادر بياناتها.

### الأعمال

1. اعتماد `StatusBarEntry` كعقد immutable يحتوي على الأقل:
   - `id`, `name`, `text`, `alignment`, `priority`
   - `tooltip`, `ariaLabel`, `kind`
   - `onPressed` أو command typed اختياري
   - icon اختياري وبيانات حالة التقدم عند توفر الحاجة.
2. تحديد قاعدة هوية `id`: فريدة لكل مساهمة داخل التطبيق؛ لا تستخدم اسم العرض كمعرّف.
3. تحديد السلوك الافتراضي للعنصر بلا إجراء: يعرض كعنصر غير تفاعلي ولا يظهر كمفتاح/زر.
4. اعتماد مصادر معلومات الإصدار الأول:
   - عدد الأخطاء والتحذيرات: `DiagnosticsService`.
   - اللغة والملف النشط وdirty state: `EditorDocumentsController`.
   - السطر والعمود: اختيار `CodeEditorController` المنشور للمتحكم المخصص للحالة.
5. حسم العناصر التي لا تملك مصدراً الآن:
   - لا تعرض فرع `main*` ثابتاً؛ SCM مؤجل.
   - لا تدّع أن UTF-8 وLF قابلة للتغيير قبل إضافة نموذج مستند يحفظ هذه القيم.
   - لا تعرض حالة إشعار ثابتة؛ لا توجد خدمة إشعارات ضمن التطبيق حتى الآن.
6. تحديد إعدادات الحجم: الاحتفاظ بـ 22px كارتفاع أساسي؛ توثيق حد العرض/سلوك overflow أثناء التنفيذ.

### المخرجات ومعيار القبول

- قائمة أولية موثقة بالـ entries، مصدر كل قيمة، والإجراء الناتج عن النقر.
- لا يوجد عنصر في النطاق الأساسي يعتمد على بيانات افتراضية متظاهرة بأنها بيانات فعلية.
- مراجعة ما إذا كان التموضع النسبي مطلوباً عند إطلاق الإصدار الأول؛ الافتراضي تأجيله والاكتفاء بالترتيب الرقمي.

**الاختبارات:** لا يلزم كود أو اختبار في هذه المرحلة.

## المرحلة 1: نماذج العناصر وعقد الخدمة

**الهدف:** تعريف API داخلية ثابتة تستخدمها المساهمات دون اعتمادها على Widget الشريط.

### الأعمال

1. إنشاء enum للمحاذاة: `left`, `right`.
2. إنشاء enum لأنواع المظهر: `standard`, `warning`, `error`, `prominent`, `remote`, `offline`؛ أطلق فقط الأنواع التي لها أسلوب واستخدام حقيقي في التطبيق.
3. إنشاء `StatusBarEntry` immutable ومتحقق الأنواع، مع `copyWith` إن كان مفيداً لتحديث entry.
4. تعريف accessor/handle يدعم:
   - `update(entry)` لتحديث العنصر نفسه.
   - `dispose()` لإزالة العنصر وفك موارده.
5. تعريف `StatusBarService` كـ `ChangeNotifier` أو controller واحد مناسب لنمط المشروع، بعمليات:
   - `addEntry(...)`
   - `entries` للقراءة دون كشف قائمة قابلة للتعديل.
   - `isEntryVisible(id)`, `setEntryVisible(id, visible)`.
   - إشارة تحديث واحدة مفهومة للمستهلك.
6. إضافة `StatusBarScope` على نمط الـ scopes الموجودة، وحقن الخدمة من `main.dart`.
7. ضمان أن الاستدعاء قبل تركيب الواجهة مسموح: يحتفظ المدير بالبيانات، وعند تركيب الشريط يرسم الحالة الحالية.

### الملفات المرجحة

- `lib/core/statusbar/models/status_bar_entry.dart`
- `lib/core/statusbar/models/status_bar_alignment.dart`
- `lib/core/statusbar/models/status_bar_entry_kind.dart`
- `lib/core/statusbar/status_bar_service.dart`
- `lib/core/statusbar/status_bar_scope.dart`
- `lib/main.dart`

### الاختبارات ومعيار القبول

- اختبار إنشاء entry والتحقق من الحقول الأساسية.
- اختبار أن `entries` لا يسمح بتعديل الحالة الداخلية.
- اختبار الإضافة والتحديث والإزالة، بما فيها dispose المكرر بأمان وفق العقد المعتمد.
- اختبار إضافة entries قبل وجود مستمع UI ثم قراءة القائمة كاملة.
- `flutter analyze` لا يظهر أخطاء جديدة.

## المرحلة 2: نموذج العرض والترتيب والرؤية

**الهدف:** جعل مصدر الحقيقة لترتيب العناصر وإخفائها مستقلاً عن ترتيب بناء Widgets.

### الأعمال

1. إنشاء `StatusBarViewModel` أو إبقاء مسؤولياته داخل الخدمة إذا ظل الحجم صغيراً؛ لا تنشئ طبقتين متطابقتين للبيانات.
2. ترتيب العناصر حسب:
   1. المحاذاة.
   2. الأولوية التنازلية داخل كل جهة (الأكبر أقرب إلى بداية الجهة).
   3. تسلسل إدراج ثابت عند تعادل الأولوية.
3. التعامل مع IDs المكررة بشكل صريح. الخيار المرجح: منع التكرار برفع خطأ/Assertion في التطوير، لا حذف عنصر آخر بصمت.
4. الإخفاء حسب ID على مستوى كل مساهمة، مع إخفاء جميع العناصر ذات ID نفسه فقط إذا كان العقد يسمح بالتكرار عمداً.
5. بث تغيير القائمة والرؤية كي يعيد Widget بناء الجزء المطلوب فقط.
6. تأجيل التموضع النسبي `location` و`compact` إلا إذا كانت مساهمات فعلية تحتاجه؛ إذا اعتمد:
   - إضافة تعريف typed للمرجع والمحاذاة النسبية.
   - fallback رقمي عند غياب المرجع.
   - منع الدوران المرجعي أو كسر العلاقات المتسلسلة.
   - اختبارات الترتيب للمراجع الموجودة والمفقودة والمتداخلة.

### الاختبارات ومعيار القبول

- أولوية أعلى/أدنى، تعادل الأولوية، فصل مجموعتي اليسار واليمين.
- الإضافة والتحديث لا تكرر العنصر ولا تغير هويته أو ترتيب إدراجه بلا داعٍ.
- إخفاء عنصر ثم إظهاره يحدّث حالة العرض مرة واحدة لكل انتقال.
- إلغاء/إزالة عنصر مخفي لا يعيد ظهوره.
- الترتيب المرجعي، إن نفذ، يغطي المرجع المفقود وإضافة المرجع بعد العنصر التابع وحذف المرجع.

## المرحلة 3: عرض الشريط والعنصر وتطبيق التصميم

**الهدف:** تحويل الواجهة الحالية من قائمة صلبة إلى renderer يستند إلى الخدمة.

### الأعمال

1. تعديل `StatusBarWidget` ليقرأ الخدمة من `StatusBarScope` ويرسم مجموعتي اليسار واليمين.
2. إنشاء `StatusBarItemWidget` مسؤول عن عنصر واحد:
   - الأيقونة والنص.
   - الـ tooltip.
   - النقر فقط عندما يكون الإجراء موجوداً.
   - لون/خلفية بحسب `kind`.
   - حد العرض والاقتطاع الآمن.
3. الحفاظ على `EditorConstants.statusBarHeight == 22`.
4. تحديث `EditorThemeData` لإضافة ألوان hover/focus والحالات التحذيرية والخطأ والتمييز، أو ربطها بألوان موجودة إذا كان ذلك يحافظ على وضوحها.
5. استخدام `Row` مرن:
   - اليسار `Expanded` أو ما يعادله لدفع الطرف الأيمن إلى الحافة.
   - اليمين محاذى للنهاية مع overflow قابل للتمرير/إخفاء محسوب، لا `RenderFlex overflow`.
   - عدم السماح لكل النصوص بفرض عرض أدنى غير محدود.
6. إزالة العناصر الثابتة التي لا مصادر لها، واستبدالها مؤقتاً بعدد قليل من entries ثابتة داخلياً فقط خلال الانتقال إن احتاجت المرحلة ذلك؛ تزال بعد ربط المساهمات.
7. إضافة Focus/hover/pressed/disabled states بحيث تكون مرئية في الثيم الداكن، مع عدم الاعتماد على `Tooltip` وحده لإيصال الاسم.

### الملفات المرجحة

- `lib/parts/statusbar/statusbar_widget.dart`
- `lib/parts/statusbar/statusbar_item_widget.dart`
- `lib/core/theme/editor_theme.dart`
- `lib/core/constants/editor_constants.dart`
- `lib/layout/widgets/workbench_scaffold.dart` (فقط إذا تطلب حقن الشريط أو تنظيم الـ scopes تعديلاً)

### الاختبارات ومعيار القبول

- Widget test يرسم عناصر من جهتي المحاذاة وبالترتيب المتوقع.
- تحديث خدمة entry ينعكس على النص والأيقونة دون إعادة تهيئة الخدمة.
- العنصر بلا callback لا يبدو قابلاً للنقر.
- عدم وجود overflow عند عرض ضيق أو نص طويل أو مجموعة عناصر كبيرة.
- ثبات الارتفاع عند 22px في الحالة الأساسية.
- التحقق من درجات foreground/background في الأنواع المدعومة.

## المرحلة 4: ربط حالات المحرر والتشخيصات

**الهدف:** جعل بيانات الشريط تعكس المستند النشط وموقع المؤشر والتشخيصات الفعلية.

### 4.1 حالة المؤشر والاختيار

1. إضافة `EditorStatusController` صغير يحتفظ بالمسار/هوية التبويب النشط وموقع المؤشر الحالي (صفر-أو-واحد-index يحدد في العقد).
2. يرسل `_CodeEditorSurface` تحديثاً عند تغير `TextEditingValue.selection` حتى عندما لا يتغير النص؛ لا تكتفِ بـ listener لا يعمل إلا على تغيّر المحتوى.
3. لا تنشئ أو تحتفظ بمراجع إلى عدة `TextEditingController` بعد التخلص منها. نشر قيمة بسيطة فقط يحمي دورة الحياة.
4. عند تبديل الملف أو إغلاقه أو فقدان المحرر النشط، امسح/حدّث الحالة كي لا يظهر موضع مستند سابق.
5. إضافة مساهمة تعرض `Ln n, Col n`؛ النقر يربط لاحقاً بأمر انتقال إلى سطر فقط إذا نفذ حوار/أمر Go to Line فعلياً، وإلا يكون العنصر للعرض فقط حتى ذلك الحين.

### 4.2 حالة اللغة والملف

1. استخدام `EditorDocumentsController.activeTab` لاستخراج اسم اللغة ومسار الملف.
2. إظهار `Plain Text` عند غياب التبويب أو `plaintext`؛ استخدم label مقروءاً لا `toUpperCase()` اعتباطياً.
3. اختبار تبديل التبويبات، وعدم وجود ملف نشط، وتغير اللغة إن أضيف تعديل اللغة.

### 4.3 التشخيصات

1. إنشاء مساهمة مستقلة تعتمد `DiagnosticsService` وتعرض مجموع الأخطاء والتحذيرات.
2. لا تعرض عدداً صفرياً إن كانت سياسة الواجهة تقضي بإخفاء العنصر عند الصفر؛ اختر سلوكاً واحداً وثبته بالاختبار.
3. النقر يفتح تبويب Problems ويظهر اللوحة، مع عدم استدعاء `togglePanel` إذا كانت اللوحة ظاهرة ولكن التبويب النشط مختلف؛ يجب اختيار تبويب Problems مباشرة.
4. استخدام ألوان `error` و`warning` مع تسمية وصول واضحة وتلميح يصف الأعداد.
5. استمع إلى تحديث الخدمة وأعد حساب عناصر status bar، مع إزالة المستمع عند التخلص.

### الملفات المرجحة

- `lib/core/statusbar/editor_status_controller.dart`
- `lib/core/statusbar/contributions/editor_context_status.dart`
- `lib/core/statusbar/contributions/diagnostics_status.dart`
- `lib/main.dart`
- `lib/parts/editor/editor_area_widget.dart`
- `lib/layout/controllers/layout_controller.dart` (إضافة عملية اختيار تبويب Problems إذا لم تكن متاحة)

### الاختبارات ومعيار القبول

- تغيير selection دون تغيير النص يحدّث line/column.
- تحديد متعدد الأسطر يعرض الموضع النشط وفق العقد المحدد.
- تبديل الملف يحدّث اللغة وموقع المؤشر ولا يعرض بيانات الملف السابق.
- تحديث diagnostics يغير أعداد الأخطاء والتحذيرات؛ مسح التشخيصات يعيد الحالة الصحيحة.
- النقر على المشكلات يظهر اللوحة على تبويب Problems حتى لو كان تبويب آخر مفتوحاً.

## المرحلة 5: إجراءات القائمة وإخفاء العناصر وتفضيلات المستخدم

**الهدف:** إدارة العناصر كما يدير المستخدم عناصر VS Code من دون جعل إخفائها يؤثر على ظهور الشريط نفسه.

### الأعمال

1. إنشاء `PopupMenuButton` أو قائمة سياق مناسبة لكل عنصر، وتشمل:
   - إخفاء هذا العنصر.
   - إظهار/إخفاء العناصر المعروفة عند النقر على خلفية الشريط.
   - إخفاء/إظهار شريط الحالة ككل، إذا كان ذلك مناسباً على المنصة.
2. إضافة `toggleStatusBar()` إلى `WorkbenchLayoutController`، وإبقاء `WorkbenchScaffold` هو مالك رؤية الجزء.
3. اختيار آلية تخزين تفضيلات مخفية العناصر:
   - أضف واجهة `StatusBarPreferencesStore` قابلة للاختبار والحقن.
   - استخدم مخزن المشروع/المنصة المعتمد إن وجد؛ لا يوجد حالياً مخزن تفضيلات عام ظاهر في البنية التي جرى فحصها.
   - إذا لم يوجد، أضف `shared_preferences` كاعتماد مقصود، مع تغليف القراءة/الكتابة وعدم ربط `StatusBarService` مباشرة بالتنفيذ.
4. استعادة IDs المخفية عند تهيئة الخدمة قبل الرسم لتجنب وميض العناصر.
5. التزامن مع فشل التخزين: لا تعرض نجاحاً زائفاً؛ سجل الخطأ أو أظهر تنبيهاً وفق نمط التطبيق، مع إبقاء الواجهة بحالة محددة.
6. إضافة أسماء واضحة لكل contribution حتى تكون قائمة الإخفاء مفهومة.
7. لا تحفظ إخفاء الشريط نفسه ضمن قائمة العناصر؛ يستمر باستخدام `isStatusBarVisible` المستقل.

### الاختبارات ومعيار القبول

- إخفاء عنصر لا يخفي الجهة الأخرى أو الشريط كاملاً.
- تفضيل الإخفاء يعاد بعد إعادة إنشاء الخدمة/التطبيق.
- حالة التخزين الفارغة أو المعطوبة لا تمنع تشغيل الشريط.
- تبديل رؤية الشريط لا يفسد حالة العناصر أو تفضيلات الإخفاء.
- Zen Mode يستمر بإخفاء الشريط وفق التخطيط الحالي، والعودة منه تستعيد حالة الظهور السابقة.

## المرحلة 6: الوصول، الاستجابة، جودة التنفيذ واختبارات التكامل

**الهدف:** إغلاق الفجوات الوظيفية قبل اعتبار المعمارية مكتملة.

### الأعمال

1. إمكانية الوصول:
   - تعيين `Semantics` واضح لكل عنصر؛ الدور button فقط عند وجود إجراء.
   - وصف مفهوم يتضمن اسم الحالة والقيمة، مثل عدد الأخطاء وموضع المؤشر.
   - دعم keyboard focus والتنقل بين العناصر، مع أمر/اختصار فقط عند وجود نظام اختصارات مناسب.
   - إظهار focus indicator واضح، وعدم الاعتماد على اللون وحده لتمييز warning/error.
2. الاستجابة:
   - اختبر عرض نافذة صغيراً وكبيراً.
   - احم العناصر المهمة من اختفاء غير متوقع؛ إن اعتمد overflow scrolling، تأكد من إمكانية الوصول للعناصر خارج الجزء المرئي.
   - احترم `TextScaler`، أو حدد حدوداً صريحة إذا كان ارتفاع الشريط ثابتاً، وغط ذلك باختبارات.
3. دورة الحياة والأداء:
   - كل مساهمة تتخلص من accessor ومستمعاتها عند إزالة الخدمة/التطبيق.
   - تغيير قيمة entry واحدة لا يعيد بناء بقية العناصر بلا داعٍ إذا أصبح ذلك مكلفاً.
   - لا تنشئ listeners من داخل `build` دون ربطها بدورة حياة واضحة.
4. إضافة اختبارات تكامل تربط `EditorDocumentsController`, `DiagnosticsService`, `StatusBarService`, والـ Widget.
5. تحديث README أو ملاحظات المشروع فقط إذا احتاج المطورون معرفة طريقة إضافة contribution جديدة؛ توثق طريقة الإضافة في تعليق API أو مستند معماري، لا في ملفات التخطيط المؤقتة.

### بوابة القبول النهائي

- `flutter analyze` نظيف من الأخطاء التي أدخلها التنفيذ.
- `flutter test` يمر، مع اختبارات statusbar الجديدة واختبارات `widget_test.dart` ذات الصلة.
- يظهر الشريط افتراضياً عند بدء التطبيق، ويتصرف مع Zen Mode كما كان قبل التغيير.
- تتحدث بيانات اللغة والموقع والتشخيصات فور تغير مصدرها.
- لا توجد callbacks فارغة لعناصر يفترض أنها تفاعلية.
- لا يوجد overflow في أحجام الشاشات المدعومة.
- dispose للخدمة أو contribution لا يترك تحديثات أو مستمعات بعد إزالة العنصر.

## المرحلة 7: مساهمات مستقبلية اختيارية

لا تبدأ هذه المرحلة قبل اكتمال بوابة القبول السابقة ووجود متطلبات فعلية.

### إضافات مستقبلية محتملة

- **SCM:** بناء خدمة/حالة Git حقيقية أولاً، ثم contribution للفرع والمزامنة؛ لا تملأها بنص ثابت.
- **Encoding / EOL / Indentation:** إضافة metadata للمستند وعمليات تغيير حقيقية، ثم عناصر تفتح أدوات الاختيار.
- **Notification status:** ربط مصدر الإشعارات الفعلي إن أضيف.
- **Progress:** تعريف نموذج تقدم يحدد loading/syncing وإيقافه عند اكتمال المهمة.
- **Relative location / compact groups:** تنفيذ إذا احتاجت العناصر المتجاورة grouping؛ أضف حماية ضد المراجع المفقودة والدورات.
- **إعادة ترتيب المستخدم:** لا تخزن ترتيباً مخصصاً قبل وجود واجهة واضحة وحل تعارضه مع ترتيب contribution priorities.
- **إضافات خارجية:** لا تنفذ إلا مع تصميم صريح لعزل الصلاحيات، دورة الحياة، التعريفات، والتحديثات؛ `StatusBarService` الداخلي وحده ليس API آمنة للإضافات.

لكل مساهمة مستقبلية: حدد المصدر، مالك الحالة، شروط العرض، الأثر على النقر، التلميح، تسمية الوصول، معرّفاً مستقراً، واختباراً لوضع غياب المصدر.

## 7. خطة الاختبارات المجمعة

| الطبقة | أمثلة الاختبارات |

| النماذج | القيم الافتراضية، copy/update، أسماء IDs، عدم قبول بيانات عرض غير صالحة. |

| عنصر UI | النص/الأيقونة، tooltip، callback، disabled، semantics، kinds، النص الطويل. |
| المحرر | تغير المؤشر فقط، تغيير النص والاختيار، تبديل الملف واللغة، عدم وجود tab. |
| التشخيصات | أخطاء/تحذيرات/صفر/clear، فتح تبويب Problems. |
| التخطيط | toggle status bar، Zen Mode، أحجام متباينة، بقاء الارتفاع. |

## 8. مخاطر وقرارات يجب عدم تأجيلها

| الخطر | المعالجة |
| --- | --- |
| خلط حالة المستند مع إدارة entries | اجعل `EditorStatusController` ينشر snapshot بسيطاً؛ لا تجعل status service يقرأ تفاصيل TextField مباشرة. |
| callbacks شكلية | لا تعرض entry على أنه زر إلا إذا كان له فعل حقيقي. |
| بيانات ثابتة مضللة | أزل الفرع/الترميز/EOL/الإشعارات الثابتة أو أخفها حتى توفير مصدرها. |
| استهلاك rebuild واسع | ابدأ بمستمع على الخدمة؛ حسّن إلى `Listenable` لكل entry فقط إن أثبت القياس الحاجة. |
| استعادة تفضيلات غير موثوقة | عالج JSON/قيمة التخزين غير الصالحة صراحة وسجل المشكلة وفق سياسة المشروع. |
| overflow في الشاشات الضيقة | اختبر مبكراً في المرحلة 3؛ لا تؤجل علاج القيود إلى ما بعد الإضافة. |
| تعارض الإخفاء مع IDs المشتركة | قرر uniqueness في المرحلة 0 واختبره في المرحلة 2. |
| تضخم تقليد VS Code | طبق العقد والسلوك اللذين تحتاجهما Flutter؛ أجّل extension host والنوافذ المساعدة. |

## 9. تعريف «مكتمل»

يعتبر التنفيذ الأساسي مكتملاً عندما تكون مراحل 0–6 منجزة، وتكون العناصر المرئية نابعة من مصادر حالة حقيقية، والخدمة مستقلة عن Widget العرض، وتفضيلات الإخفاء محفوظة، والتخطيط الحالي مستمر في العمل، والاختبارات والتحليل الساكن ناجحين. لا تعد العناصر المستقبلية في المرحلة 7 شرطاً لإصدار Status Bar الأساسي.
